第一章：AI 给测试带来了什么变化

过去，自动化覆盖范围主要受脚本建设、维护以及环境数据成本约束：脚本生产慢、维护成本高、环境和数据准备复杂，很多需要重复验证的场景只能依赖人工。

1.1 【看过去】AI介入前，传统的自动化测试如何运转

我们基于源码复盘了某知名互联网公司大型资讯 App 的传统自动化体系：

我把这套方案总结成三个词：共建、复利、运营。

第一，共建。开发写单测和组件测试，覆盖代码变化，并提供可调用、可编排的业务原子能力；测试把这些能力串成E2E流程，持续沉淀公共步骤、公共用例和场景数据；框架统一提供Mock、Checkpoint和断言。

第二，复利。资产越丰富，新增测试就越像搭积木，边际成本越低，稳定性和可用性也越高。

第三，运营。它不是一次性建设，而是长期协作。一旦投入中断，业务、接口和数据继续变化，测试资产会快速劣化，重新恢复的成本可能接近一次重构。

核心不是某个框架，而是持续共建、复用和运营测试资产的能力。

AI Agent带来的机会：AI Agent能根据需求和代码变化，自动生成、执行和维护用例、Mock及检查点，显著降低长期维护成本。

第二章：开发和测试协作模式的转变

2.1 测试左移的目的是缩短交付路径

测试左移减少“开发完成—提测—发现问题—退回修改”的串行往返。

2.2 需求视角的分工

【边界清晰、风险较低的需求】开发掌握最完整的需求和代码上下文。Test Agent帮助开发在编码过程中完成单元测试、组件测试和本次变更的主要场景验证。开发交付的不再只有代码，还包括已经验证的范围和仍然存在的风险。

【复杂项目】涉及多个团队、模块和系统，没有单个开发能够掌握全部上下文。QA需要提前识别跨系统风险，制定测试范围和质量标准，组织系统级验证，并对发布条件进行把关。

分工的边界取决于风险和系统跨度：

单模块、低风险需求，以开发和Test Agent验证为主；跨团队、跨系统或高风险项目，由QA负责整体测试策略和系统性保障；无论项目大小，开发都需要完成本模块自测；无论需求多小，资金、权限和数据安全等高风险改动都不能跳过专业验证。

2.3 测试分层，自动化测试框架下开发和测试的分工

测试层级越低，反馈越快、修复成本越低、开发责任越强；测试层级越高，场景越复杂、修复成本越高、测试专业判断越重要。

3.2 Harness

我们把 Agent 和 Harness 的职责进行了拆分：

Agent 负责理解需求、探索代码、生成候选方案，处理不确定性。Harness 掌握流程权、状态权、验收权和恢复权，保证过程确定。人负责关键业务判断和复杂失败的最终决策。

Harness 主要解决四件事：

流程确定：通过任务拆解、DAG 和状态机，明确执行顺序和完成条件。输入确定：以需求、用例和测试 Spec 限定测试范围、前置条件和验证目标。结果确定：测试代码必须经过机器校验、人工评审和真实执行。失败收敛：只允许有限重试和定向修复，疑似业务问题立即转人工。

3.3 客户端

客户端测试的主要难点，是把需求和页面语义转换成可以在真实设备上稳定执行的测试代码。

QA流程使用单独的pipeline，和开发流程分开，除了少数节点有依赖，大部分节点并行；QA 流程 All in WebUI，规范操作路径；测试spec first，用例 -> 测试spec -> 测试生码 -> 执行

在 Harness 层面，客户端主要建立了三层控制：

生成前有约束：需求、用例和测试 Spec 共同限定生成范围。生成后有验收：机器校验完整性、一致性和可执行性，关键业务判断由人确认。交付前有实证：测试代码必须在真实环境执行，并携带日志、覆盖情况和测试报告。

工程实现上，我们进一步做了几项收敛：

Test Agent 与开发 Agent 会话隔离，避免上下文膨胀和注意力稀释。确定性步骤脚本化、Tool 化，减少 Skill 嵌套调用中的跳步。将测试生码规则从会话提示词提升为正式 Spec。QA 操作路径统一收口到 WebUI，减少流程分叉。补齐账号、测试数据、Mock 和环境准备能力。

当流程约束稳定后，低成本模型同样可以完成大部分标准化任务。模型能力仍然重要，但流程可靠性不再完全依赖模型能力。

3.4 服务端

服务端测试强依赖代码变更和内部业务状态。当前主要采用串行模式：开发完成后，部署远端 => sepc => 文本用例 => 脚本代码 => 执行

关键节点：

运行环境是否正确；前置数据是否可信；返回成功后，内部状态和业务副作用是否符合预期；测试失败诊断：来自测试资产、运行环境，还是业务代码。

因此，服务端 Harness 控制四个环节：

执行前受控：校验测试契约和环境能力，准备账号、配置和测试数据，并完成状态隔离和现场快照。执行中可观测：调用真实 HTTP、Bean 或 RPC，同时通过 SQL、日志、Snapshot、Checkpoint 等方式观察内部状态。执行后可证明：不仅验证返回值，还验证业务状态和副作用，并保存步骤、快照和检查点。失败后可收敛：先自愈，再转人工

基于现在流程的基础上，有几个关键改进方向：

测试结果和SDD loop结合，出现问题，提供上下文驱动ai自己调试和修复；缺什么：ai在runtime的调试能力、流程串联复利工程：测试数据、步骤、断言、用例资产化；缺什么：流程串联、业务沉淀不追求全自动化E2E，复杂场景半自动化，人要发挥作用：mock、执行步骤自动化；结果断言人review（过程透明易懂，提升review效率）
