三代知识检索范式：RAG/GraphRAG/LLM Wiki，检索解决不了理解的问题

作者：科技风向标 发表：2026-07-02T16:11 来源：今日头条 下载：2026-07-03

搭了一套 RAG，接上向量数据库，文档丢进去，问题问出来——感觉很完整。

但你有没有遇到过这样的情况：同一个问题，有时候答得很好，有时候答得一塌糊涂；同一份文档里的信息，明明就在那里，却怎么都检索不到；知识库用了半年，感觉它没有"成长"，只是变得更大了。

这不是你的实现有问题，这是 RAG 的设计哲学决定的。

2026 年，知识检索这件事正在经历一次范式迁移。理解这三代范式——RAG、GraphRAG、LLM Wiki——不是为了追新，而是为了在下次选型时，不再走弯路。

第一代：RAG——把检索权交给查询

RAG（Retrieval-Augmented Generation）的逻辑非常朴素：我不把知识烧进模型，而是在你问问题的时候，实时去文档库里捞相关片段，拼进 prompt 给 LLM 看。

这套路有几个天然优势：

  • • 部署成本低 ：文档丢进向量数据库，向量化就完事，不需要微调模型
  • • 知识更新方便 ：换个文档，重新索引，完全不动模型
  • • 可溯源 ：每次回答附带原始文档片段，来源清晰

代表项目：

  • • LangChain （⭐141k）：已从 RAG 框架演进为智能体工程平台（agent engineering platform），覆盖更广泛的 LLM 应用开发
  • • LlamaIndex （⭐50.6k）：从 RAG 框架发展为文档智能体平台，提供 OCR + Agent 能力，支持复杂文档理解
  • • Chroma （⭐28.7k）、 Qdrant （⭐32.9k）：向量数据库，RAG 的基础设施

但 RAG 的局限也很明显。

RAG 的检索单元是片段，不是知识。 你检索到的东西，是文档里的一段话，而不是经过整合的概念。如果一个问题的答案分散在 5 篇文档的不同位置，RAG 可能同时捞到这 5 个片段，也可能一个都捞不到——完全取决于语义相似度打分。

更根本的问题是： RAG 是"解释器模式" 。每次有新文档进来，不加处理就存进去；每次查询，临时做检索拼接，临时让 LLM 推理。知识从来没有真正被"理解"和"整合"，只是被存起来等人用。

用一个比喻：RAG 就像一个图书馆——书很多，但没有人读过它们，只有一个会根据关键词找书的馆员。你问的问题越复杂，需要跨越多本书的信息越多，这个馆员就越力不从心。

第二代：GraphRAG——引入关系结构

微软在 2024 年推出的 GraphRAG （⭐34k），在 RAG 的基础上引入了知识图谱。

它的工作方式是： 在 Ingest（摄取）阶段就做实体抽取和关系识别 ，把"苹果公司的 CEO 是谁"这类关系显式存成图谱中的三元组，而不只是一段段文字。查询时，可以在图谱上做多跳推理——比如"A 的老板的老板是谁"——这类需要连接多个节点的问题，向量检索根本做不到，但图谱天然支持。

相关项目：

  • • microsoft/graphrag （⭐34.1k）：微软官方实现，支持 Global Search 和 Local Search 两种查询模式
  • • HKUDS/LightRAG （⭐37.2k，EMNLP 2025）：港大团队出品，把图谱检索做得更轻量。相比 GraphRAG，LightRAG 查询延迟降低 10-100 倍，存储成本显著减少，生产可用性更强
  • • gusye1234/nano-graphrag （⭐3.9k）：极简 GraphRAG 实现，核心代码仅 1100 行，适合学习原理和快速实验

GraphRAG 适合的场景很具体： 文档中存在大量实体，且实体之间的关系对回答至关重要 。比如法律文书分析、企业知识图谱、生物医学关系抽取。如果你的查询经常是"A 和 B 之间的关系是什么"，GraphRAG 是对的。

LightRAG 的性能优势 （来自 EMNLP 2025 论文）：

  • • 查询延迟比 GraphRAG 降低 10-100 倍
  • • 存储开销显著减少，更适合大规模部署
  • • 如果 GraphRAG 在你的场景里太重，LightRAG 是更好的起点

但 GraphRAG 也有代价：

  • • 图谱构建成本高，需要复杂的实体识别和关系抽取流水线
  • • 图谱的质量高度依赖数据质量，噪声难以过滤
  • • 对于叙述性、概念性、主观判断类的知识，强行抽成三元组往往丢失大量语义信息

GraphRAG 解决了 RAG 的多跳推理问题，但它本质上还是在"查询时"做推理，只是把推理的基础从文本片段换成了图谱节点。知识本身，依然没有被真正"理解"。

第三代：LLM Wiki——把综合从查询时前移到摄取时

这才是 2026 年最值得关注的范式转变。

Karpathy 在 2026 年 4 月抛出了 LLM Wiki 的概念，核心思路是： 不要在查询时才让 LLM 理解文档，而是在文档进来的那一刻，就让 LLM 把它"编译"成结构化的知识资产 。

用一句话概括： LLM Wiki 是编译器模式，RAG 是解释器模式。

三层存储架构

LLM Wiki 把知识分成三层来管：

Raw 层 ——原始文档，原封不动保存。这是信息的"一手来源"，永远不修改。

Wiki 层 ——经过 LLM 处理后的知识页面。这才是真正的核心。每一页对应一个概念、一个人物、一个系统组件或一个事件，里面的内容是 LLM 综合了多份原始文档后，主动提炼的知识摘要、关联概念、置信度标注，以及"这个结论来自哪些原始文档"的溯源信息（provenance）。

Schema 层 ——结构化的元数据索引，记录哪些 Wiki 页面存在、它们的 frontmatter 字段是什么、知识图谱的骨架在哪里。

Ingest 流水线：知识的"编译"过程

每次有新内容进来，LLM Wiki 会执行这样一套流程：

  1. 1. 读取原始文档 ，理解核心观点
  2. 2. 查询现有 Wiki 索引 ，找到相关的已有页面
  3. 3. 判断是否存在矛盾 ：新内容和已有知识冲突时，显式标注，不偷偷覆盖
  4. 4. 创建或更新实体页、概念页 ：把新知识整合进已有的知识网络
  5. 5. 建立双向链接 ：页面之间互相引用，形成知识图谱
  6. 6. 更新索引和日志 ：记录这次 Ingest 改变了什么

最关键的一点： 第 10 篇文档进来的时候，知识库已经不只是 10 篇文章的集合，而是一个经过 LLM 反复整合、交叉引用、矛盾标注的知识网络 。这就是复利。

当然，这种「编译」也有代价：

  • • 信息丢失风险 ：Ingest 阶段的摘要和综合可能丢失原文的细节。对于需要精确引用的场景（法律、医疗、审计），必须配合 Raw 层原文访问，不能仅依赖 Wiki 层
  • • LLM 依赖度高 ：Wiki 层的质量完全取决于底层模型的综合能力，模型能力不够时可能引入系统性偏差
  • • 构建成本 ：相比 RAG 的即时索引，LLM Wiki 需要消耗更多 Token 和时间进行 Ingest 处理

开源实现

luotwo/llm-wiki （⭐188，活跃更新中）是目前最完整的 LLM Wiki 开源实现，包含：

  • • 完整的 Skill 文件（可接入 Claude Code）
  • • Raw/Wiki/Schema 三层目录结构
  • • Ingest/Query/Lint 三大操作的完整工作流
  • • 实战经验总结（包括微信公众号反爬绕过方案、页面命名规范等）

配合 Obsidian 使用体验最佳——Obsidian 的图谱视图可以直观呈现 Wiki 页面之间的关联网络，Dataview 插件可以基于 frontmatter 生成动态表格。

按查询类型路由

LLM Wiki 还支持 Adaptive RAG——根据查询类型动态决定用什么方式回答：

  • • 事实型查询 （"某模型的参数量是多少"）：直接查 Wiki 页面
  • • 推理型查询 （"为什么 MoE 架构比 Dense 架构更适合超大参数模型"）：读取多个相关 Wiki 页面，让 LLM 在页面内容基础上推理综合
  • • 探索型查询 （"帮我梳理当前 RAG 的主要流派"）：先扩充 Wiki，再基于丰富的 Wiki 内容回答

另一个方向：STORM——让 AI 主动做研究

在讨论这三代范式的同时，还有一个值得关注的项目走了不同的路： stanford-oval/storm （⭐30k）。

STORM 不是让你把文档丢进去，而是给它一个主题，它会自动：

  1. 1. 生成多角度的研究问题
  2. 2. 模拟不同专家视角进行多轮对话
  3. 3. 检索外部资料
  4. 4. 综合生成带引用的完整报告

这更像是 LLM Wiki 的"主动研究"模式——不是被动摄取你给的文档，而是主动去找知识、综合知识。STORM 在 EMNLP 2024 上发表，已经有生产级的 Ko-STORM 等衍生版本。

还有一个维度：记忆层

知识库之外，还有一个更轻量的方向—— AI 记忆层 。

mem0ai/mem0 （⭐60k）做的事情是：不管你用什么 LLM 应用，它在底层维护一个跨会话的用户记忆，记住你的偏好、历史决策、个人上下文。这不是文档检索，而是"记住你这个人"。

它和 LLM Wiki 的区别在于：LLM Wiki 是知识的编译和整合，mem0 是用户行为和偏好的持续记录。两者可以互补——一个管"世界知识"，一个管"关于你的知识"。

其他值得关注的项目

除了上述三代范式代表，还有几个项目值得了解：

R2R (SciPhi-AI) —— "The most advanced RAG framework"

  • • 生产级 RAG 方案，支持多模态（文本、图片、音频）
  • • 提供完整的 RAG pipeline，包括解析、嵌入、检索、重排序
  • • 适合需要快速搭建企业级知识库的场景

RAGFlow (InfiniFlow)

  • • 强调"深度文档理解"的 RAG 引擎
  • • 在复杂表格、多栏排版、图文混排等场景的解析能力突出
  • • 适合处理版式复杂的业务文档（财报、论文、手册）

FlashRAG (NJU)

  • • 南京大学出品的 RAG 基准测试框架
  • • 提供 32 个基准数据集和 15 种基线方法
  • • 学术研究领域评估 RAG 系统的重要工具

实际成本参考（估算）

如果你要落地，除了技术选型，还要考虑实际成本。以下是以 GPT-4o 为例的粗略估算（处理 1000 页文档）：

阶段 RAG GraphRAG LLM Wiki
Ingest 构建成本 $5-10（仅嵌入） $50-100（实体抽取+关系识别） $80-150（全文理解+综合+链接）
单次查询成本 $0.01-0.05 $0.02-0.10（图谱遍历） $0.01-0.03（直接查页面）
存储成本 低（向量库） 中（向量+图谱） 中（Raw+Wiki+索引三层）

成本决策要点 ：

  • • RAG 是"重查询、轻构建"，适合频繁更新文档的场景
  • • GraphRAG 和 LLM Wiki 是"重构建、轻查询"，构建一次后可以高频复用
  • • LLM Wiki 的前期投入最大，但随着知识积累，边际收益递增

什么时候该用哪个

用 RAG 的情况 ：知识库体量不大，更新频繁，对知识之间的关联性要求不高，只需要"给我相关的原文片段"这种检索能力。比如客服文档问答、企业内部知识库的快速搭建。今天大多数场景，RAG 已经够用。

用 GraphRAG 的情况 ：文档中存在大量明确实体，且实体之间的关系本身就是问题答案的一部分。比如合同分析、专利检索、生物医学知识图谱。如果你的查询经常是"A 和 B 之间的关系是什么"，GraphRAG 是对的。推荐先试 LightRAG，比 microsoft/graphrag 轻量得多。

用 LLM Wiki 的情况 ：你在做长期、深度、持续积累的主题研究，知识需要随时间不断更新和深化，而且你对知识的不确定性和矛盾性有管理需求。比如技术研究笔记、代码库理解（把代码库的架构和模块关系编译成 Wiki）、个人级别的知识管理。

不适合用 LLM Wiki 的情况 ：需要精确引用原文的法律、医疗、审计场景；文档频繁更新且需要即时生效的场景；预算有限无法承担 Ingest 阶段 API 成本的场景。

几点判断

LLM Wiki 不是 RAG 的升级版，它们解决的是不同阶段的问题。 RAG 解决的是"如何在查询时找到相关内容"，LLM Wiki 解决的是"如何在内容进入系统时就把它变成可用的知识"。两者可以共存——你完全可以在 LLM Wiki 之上再跑一层 RAG，把 Wiki 页面本身当成检索单元。

LLM Wiki 的价值主张很吸引人，但落地有门槛。 它的效果高度依赖 LLM 在 Ingest 阶段做综合的质量。如果模型能力不够，生成出来的 Wiki 页面可能引入系统性偏差，比直接存原文更危险。这不是说 LLM Wiki 不好，而是说它对底层 LLM 的要求更高。

幻觉回写是一个需要认真对待的闭环风险。 Save 操作允许 LLM 把自己的推理结论写回 Wiki，这在设计上很优雅——知识系统能自我进化。但如果 LLM 的某次推理出了偏差，这个偏差会被"合法化"写入 Wiki，后续所有基于该 Wiki 页面的查询都会被污染。置信度字段和矛盾标注字段是对抗这一风险的机制，但它们不是银弹。

信息丢失是另一个隐形成本。 LLM Wiki 的 Wiki 层是"综合后的知识"，不是原文。这意味着某些细节可能在 Ingest 阶段被丢弃。对于法律、医疗等需要精确追溯原文的场景，Wiki 层只能作为导航入口，最终答案仍需锚定 Raw 层的原始文本。

Karpathy 抛出这个概念，更大的意义在于提供了一个思维框架 ：我们不应该只在乎"怎么检索"，更应该在乎"知识以什么形态存在"。原始文档是一种形态，向量是一种形态，图谱是一种形态，而经过 LLM 理解和综合的知识页面是另一种形态——每种形态背后都有对应的操作语义和适用边界。

最后

三个范式没有绝对的优劣，只有合不合适当前的场景。

RAG 是今天最成熟、落地最容易的方案；GraphRAG 在关系密集型场景下提供了 RAG 无法比拟的推理能力；LLM Wiki 则代表了一个更大的野心——让 AI 系统真正拥有持续沉淀、自我演化的"长期记忆"。

知识工程这件事，越早想清楚范式，后面重构的代价越小。

如果你现在在搭 RAG 系统，这三个框架值得放在一起比较着想，而不是"RAG 好用就 RAG 到底"。
