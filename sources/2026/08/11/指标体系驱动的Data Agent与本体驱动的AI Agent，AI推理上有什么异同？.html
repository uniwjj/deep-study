首先讲清楚，指标体系驱动的Data Agent与本体驱动的AI Agent的推理方式不一样。而且正是这种不一样，决定了它们适合解决完全不同的问题。

这不是一个理论问题。在过去两年里，几乎所有尝试构建“数据智能助手”的团队，都会在某个时刻撞上这道选择题：我的 Agent 应该以什么为核心来“思考”？是那些已经定义好的、躺在数据仓库里的指标？还是那张描绘业务世界概念与关系的本体图谱？

选错了，Agent 要么答非所问，要么看似聪明实则脆弱。

让我直接从结论开始拆。

它们共享同一个外壳，但内核完全不同


先看它们像的地方。

不管是Data Agent还是Ontology Agent，只要冠上“Agent”之名，它们都遵循同一个宏观循环：接收自然语言目标 → 拆解为子任务 → 调用工具获取信息 → 整合信息形成回答 → 必要时反思与纠错。

都依赖 LLM 做规划和语言理解。都需要工具调用能力——一个调SQL或 OLAP API，一个调SPARQL或图数据库查询。都有记忆机制来缓存中间结果。都能在出错时自我修正。

但一旦进入“推理”这个环节，分岔就开始了。

推理的“原料”不同，推理的“路径”不同，推理的“终点”也不同。这不是程度差异，而是范式差异。下面逐一拆解。

Data Agent 的推理本质——归因与下钻


指标体系驱动的 Data Agent，它的推理空间是一个已经被高度结构化的数字空间。

这个空间由什么构成？是指标语义。每个指标都带着自己的“身份证”：计算公式、统计口径、可下钻的维度（时间、地域、品类、渠道……）、数据源、刷新频率。这是一个封闭但精确的世界。

它的典型推理链路


当一个Data Agent接到“Q3 毛利率为什么下降了”这个问题时，它的推理大致如下：

第一步：确认异常。 它先拉取 Q3 和 Q2 的毛利率快照，确认下降幅度——3.1 个百分点。这不是幻觉，这是 SQL 算出来的硬数字。

第二步：维度下钻。 这是 Data Agent 最标志性的推理动作。它沿着指标语义里预先绑定的维度树逐层切开：

  • 按地区切：华北贡献了 -2.1pp，华东 -0.6pp，其他区域持平。锁定华北。

  • 在华北内按品类切：家电贡献了 -1.8pp，3C -0.3pp。锁定家电。

  • 在家电内按渠道切：线下贡献了 -1.8pp，线上几乎为零。锁定线下。


每一步都是确定性的集合运算——GROUP BY 而已。但 Data Agent 的“智能”体现在：它知道下一步该切哪个维度，因为它正在比对各个维度的贡献度，遵循帕累托原则。

第三步：关联其他指标做交叉验证。 光下钻不够。它会继续拉“华北家电线下”的促销费用率、客单价、折扣率等关联指标，寻找解释线索。

第四步：输出归因结论。 “Q3 毛利率下降 3.1pp，主因是华北家电线下渠道促销折让扩大，贡献了 -1.8pp。”

这种推理的本质


是归纳与归因。 在已经定义好的指标空间里做维度遍历和贡献度分配。它的每一步都是可复算的——换个 Agent 来跑，只要口径一致，结果必然一致。

它的强项是精确、快速、可审计。 适合回答“掉了多少”、“掉在哪”、“谁贡献最大”这类问题。

它的天花板也很明显：指标语义里没定义的维度，它钻不下去。 如果“竞品动向”没有被做成指标，它就永远不会知道竞争对手也在降价。它的世界被指标字典框死了。

Ontology Agent 的推理本质——跳转与约束


本体驱动的 AI Agent，它的推理空间是一个开放的、关系密集的图结构。

这个空间的构成是本体语义：实体（供应商、零件、项目、法规）、关系（供应、依赖、合规、风险传导）、公理（“若 A 是 B 的子公司，则 A 涉诉会影响 B 的授信额度”）。这是一个开放但稀疏的世界——它知道很多“谁和谁有关”，但不天然知道“关联的程度是多少”。

它的典型推理链路


同样面对一个问题，但这次是“供应商 X 能不能按时交付零件 Y”，Ontology Agent 的推理完全不同：

第一步：定位实体与意图解析。 它先在本体图中找到“供应商 X”这个节点，找到“零件 Y”这个节点，找到它们之间的“供应”边。确认用户问的是交付风险。

第二步：多跳关系遍历。 这是 Ontology Agent 最标志性的推理动作。它不“下钻维度”，它“往外跳”：

  • 第一跳：X 的上游是谁？→ 原材料 Z 的矿场。

  • 第二跳：Z 矿场最近有没有异常事件？→ 本体里挂了“自然灾害”事件实体，LLM 读取挂载的新闻摘要：“局部暴雨，停工三天”。

  • 第三跳：Z 还要经物流商 W 转运。W 是否在同一受灾区域？→ 是。

  • 第四跳：X 还有其他客户吗？会不会抢产能？→ 本体里 X 的“供货给”边指向多家企业。


每一步都是一次图遍历。Agent 的“智能”体现在：它知道哪些跳是有意义的，哪些跳是噪声，并且能在适当时候停下来。

第三步：公理与规则约束。 本体里如果定义了“若供应商的任一上游原材料产地发生自然灾害，则该供应商的交付风险等级上调一级”，Agent 会自动激活这条规则，无需用户提示。这是符号推理，是确定性的。

第四步：不确定部分交给 LLM。 “局部暴雨，停工三天”的影响程度是高是低？LLM 读文本后判断为“低”。这个判断是概率性的，但被封装在规则框架内。

第五步：风险传导汇总。 把多跳路径上每段的风险概率收口，给出“供应商 X 交付零件 Y 的风险为中低”的结论。

这种推理的本质


是演绎、关联与链接预测。 在图结构上走路径，用规则做硬约束，用 LLM 做软判断。

它的强项是开放域关联。 能从一家供应商跳到矿场、跳到天气、跳到物流、跳到竞争对手。它能回答“A 和 B 之间有没有隐藏关系”、“风险会怎么传导”这类问题。这是 Data Agent 做不到的。

它的天花板同样明显：本体覆盖率决定上限。 图上没有的关系，Agent 跳不出去。而且多跳越长，幻觉和噪声累积越严重。五跳以上的推理，如果没有公理剪枝，很容易变成“万物皆有关联”的无意义输出。

融合才是真正的答案


单独看，两者各有短板。

Data Agent 能精确告诉你“指标掉了多少、掉在哪”，但到“为什么会这样”就卡住——除非那个原因恰好也被做成了指标。而现实中，大多数“为什么”的原因（竞品动作、供应链扰动、政策变化）都不是指标，而是关系和事件。

Ontology Agent 能告诉你“图上连着什么、可能传去哪”，但到“传了多少、现在数值多少”就虚——除非那条边恰好挂了指标。而现实中，大多数“传导效应”都需要量化才能指导决策。

所以真正的答案不是二选一，而是融合。

融合不是让两个 Agent 并列运行、最后拼报告。那是并联，不是融合。真正的融合是让它们在同一个推理链路上交替上场：

第一步：Data Agent 感知异常。 下钻定位到“华北家电线下 -1.8pp”。但到了维度树的叶子节点，它解释不了了。

第二步：它把“华北家电线下”这个坐标抛给 Ontology Agent。 这不是一句自然语言，而是一条结构化消息：带上指标名、下钻路径、异常幅度、未解释比例。

第三步：Ontology Agent 以这个坐标为锚点向外多跳。 发现铜价上涨、促销强度过高、竞品针对性补贴三条关联路径。它把这三条路径回传给 Data Agent。

第四步：Data Agent 对每条路径做量化回捞。 铜价传导贡献 -0.9pp，促销折让贡献 -1.8pp，份额流失贡献 -0.4pp。加起来刚好 3.1pp。

第五步：合并输出分层归因。 根因（本体侧）：铜价外生冲击加竞品针对性动作。量化（指标侧）：各因素贡献度如上。建议：收紧促销节奏、锁铜料长单、定向反击竞品主力 SKU。

这不是两个 Agent 各说各话。这是一个 Agent 的两个分身，在同一个思考链上接力。

所以回到标题的问题


指标体系驱动的 Data Agent 与本体驱动的 AI Agent，在 AI 推理上有什么异同？

同：都依赖 LLM 做规划与语言交互，都走“感知→规划→工具→反思”的 Agent 循环，都能把自然语言转成结构化查询。

异：Data Agent 的推理空间是维度树加指标字典，动作是下钻归因，答案是“多少、在哪、谁贡献”。Ontology Agent 的推理空间是图结构加公理，动作是多跳推导，答案是“连得上、怎么传、可能影响谁”。

一个擅长解释数字的变化。

一个擅长揭示事物的关联。

而真正有用的系统，不会让它们二选一。会让 Ontology Agent 先画出“可能相关的那片网”，再让 Data Agent 去网上每个节点读出“具体是多少、变了几个点”。

地图指路，仪表读数。推理才算完整。
