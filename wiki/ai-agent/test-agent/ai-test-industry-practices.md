# 业界 AI 测试实践对比（2025-2026）

云音乐在自动化测试阶段性同步（tm599）中整理的业界实践分析。（表格为原文口径）

| 公司/团队/方案 | 发布时间 | 核心机制 | 方案亮点 |
|---------------|---------|---------|---------|
| Meta／JiTTesting | 2026-02-11 | 理解 Diff 意图并构造风险变异，生成「父版本通过、当前版本失败」的测试代码；固定 Runner 执行后，再由规则、多模型和工程师确认，测试无需长期入库，专门回答「这次改动是否刚刚引入了问题」，适合快速变化的代码库 | 理解变更意图，通过变异测试生成测试，并由规则和多模型筛选候选问题（详见 [[meta-jit-testing]]） |
| 字节 Web Infra Dev／Midscene | 2025 起持续更新 | 通过 aiAct、aiTap、aiAssert 等自然语言 API，在运行时理解截图、定位元素、执行动作和判断结果；纯视觉、跨技术栈 | 统一覆盖 Web、Android、iOS、鸿蒙和桌面，可接入 Playwright、Vitest 及 YAML 流程 |
| 美团质效技术部／KuiTest | 2026-01-13 | 根据组件树、OCR、截图和图标库理解控件功能，预测交互后的预期响应；执行后再由多模态模型判断实际结果 | 重点解决传统 UI 遍历「会点击但不会判断」的 Oracle 难题，不需要为每个页面编写专用规则 |
| 快手 | 2026-07-08 | 将用例转成 AI 易理解的原子步骤、预期结果和环境依赖；Agent 通过视觉/OCR/DOM 感知页面，动态规划、操作、验证和重试 | 在「固定脚本」和「纯 AI 探索」之间选择第三条路线：用结构化测试意图约束 Agent，兼顾灵活性和可控性 |
| 小红书／质效研发部 AI Coding 团队 | 2026-05-12 | 人定义测试意图，Agent 读取 PRD 和业务知识、探索 GUI 路径并生成测试代码；验证通过后代码进入 Git 和 CI；视觉子 Agent 按需定位 | 「探索一次、固化复用」：新需求保留 Agent 灵活性，老需求使用确定性代码降低成本和波动 |
| 阿里／速卖通 | 2026-08-10 | 建设用例生成、前置构造、环境编排、自主执行、断言归因、知识回流六层体系；规划 Agent 和断言 Agent 在运行时参与 | 不只关注「AI 会不会点」，而是治理账号、配置、测试数据、环境切换和「AI 假通过」等生产问题 |
| 去哪儿 | 2026-08-17 | 需求和设计稿结构化后完成代码实现；将验收项转为 Case，在真机执行并保留截图、接口和日志证据；失败后归因、修复和重跑 | 覆盖范围最宽；通过状态机、检查点和任务恢复机制解决长时间、多 Agent 交付任务的可靠性问题 |

## 三大方向

各家技术路线不同，但方向一致：

1. **从生码到结果**：AI 开始对测试执行、结果判定和失败闭环负责
2. **从探索到复用**：新需求由 Agent 动态探索，验证成功后固化为回归资产
3. **从模型到工程**：真正的壁垒是业务知识、环境数据、可信断言和工程闭环

## 普遍流程

```
需求与变更理解 → 前置条件和数据准备 → 环境编排 → Agent 自动执行
→ 多证据可信断言 → 成功路径固化为回归资产 / 失败路径归因、修复与重跑 → 知识回流
```
