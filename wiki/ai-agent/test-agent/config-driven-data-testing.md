# 配表驱动的数据展示测试（年报五阶段）

雷火平台创新中心（张启）以永劫无间 D90 五周年年报为例的全链路 AI 测试方案。Skill 名 `ccc-qa-annual-report-testing`。

## 一、问题：数据展示分支的专项测试

游戏年报是年末/周年节点的个人数据总结活动（类「支付宝年度账单」）：数据总结页（创角时间/登录天数/段位/本命英雄等千人千面）+ 结果页（年度称号/关键词/海报）+ 任务与分享 + 他人年报（只读）。所有账号产品流程完全一样，但真实数据不同导致**同一套页面呈现成百上千种数据展示分支**。年报测试的本质并非主流程验证，而是**数据展示分支的专项测试**。

人工手段的四类局限（以本次为例：配表 85 个分支、数据库 138 个字段）：

1. 受限登录问题，测试角色池只有几个，每个数据字段反复改
2. 真数据凑不齐只能造数据，造出来的又不是真数据
3. 分支量大人工无法覆盖全，覆盖率既无法量化也难以复现
4. 配表分支/文案一改，前期构建的测试数据即告作废

目标：不逐字段手动改数、不改库嫁接、不伪造数据，直接输出可验收的年报数据结果。

## 二、核心思路：配表即预期

产品和开发维护的配表每行两个核心字段：

- **condition**（UX 数值提供）：命中条件，如 `max_level_id >= 7500 && max_level_id <= 999999999`
- **text**（产品和策划确认）：命中后页面该显示什么文案

约束：同一页面下各行 condition **互斥**（一个玩家只命中一行）；不同页面之间**正交**（可合并到同一测试账号）。condition（数据层判断）+ text（渲染层文案）合在一起就是完整的预期结果——**不需要人工为 85 个分支写用例，配表本身就是可机器执行的验收标准**；用例只描述通用执行场景，数据差异由配表驱动自动判断。

## 三、五阶段流水线：算 → 验 → 定 → 跑 → 报（+ 审）

### 算：配表 condition → 集合覆盖算最少账号

把每行 condition 翻译成「字段→典型值」的造数补丁；同页互斥分支拆给不同账号、跨页正交分支合并——经典**集合覆盖问题**，账号数收敛到「分支最多的那个驱动页的分支数」。自检：①覆盖率 ②造数命中率（condition-eval 反查每条分支是否真的被满足）。均为脱离浏览器的纯计算，跑得快、可反复迭代。

### 验：反向校验配表漏配（正向流程测不到的盲区）

正向流程隐含假设配表完整，但产品配表可能漏配枚举（如段位 DB 有 11 档、配表只配 7 档——漏掉的 4 档正向永远测不到且自检全绿）。解法：拿 DB 真实枚举/区间分布**减**配表覆盖集，差集即疑似漏配；离散枚举用 `SELECT DISTINCT` 对比，连续字段按声明的 bands 分桶计数对比。每条疑似漏配带真实玩家计数 + 可复现样本 role_id（可直接生 cookie 注入坐实）。**只报告不阻断**，是否补配表由需求方决定。

### 定：定位典型角色，直生 cookie 注入（不改库、不改归属）

典型数据挂在正式角色名下：拿到「有这份典型数据」的角色的 role_id，**role_id → JWT → 注入浏览器**即可登录展示，告别「改 ux 归属嫁接给测试账号」的老路线。两条取角色路径：新玩家（宣发有角/无角）读固定账号清单长期复用；老玩家（活跃/回流）运行时按分支 condition 只读查 ux 表（正则白名单 + 黑名单排除 QA 造数前缀）。**铁律：只采真实玩家，禁采造数据**；找不到满足分支的真实角色时如实标「⚠️无法覆盖」并写明原因，绝不回退改库凑数据。

### 跑：跑 UI（委托 playwright-mcp-testing）

不重造浏览器执行引擎，年报专属的是「逐账号循环 + 数据展示断言」包装：注入 cookie → 校验登录门禁 → 按主流程逐页翻页截图 → **四层断言**：

1. 接口层：调数据接口拿字段，用配表 condition 反查是否命中对应分支
2. 文案层：取页面渲染文本与配表该分支 text 比对关键词
3. 数值准确性：抽数据齐全的账号，页面展示值与角色真实游戏数据逐字段精校（口径/区间/派生逻辑）
4. 显示完整性：图片裁切/变形/模糊、内容越界、异常留白错位检测——量化指标 + 局部截图肉眼复核定级

**渲染就绪信号取代固定 sleep**（高频坑：翻页后页面未渲染完就截图，拿到空白页或动画中间态；年报每页数据量差异巨大，固定 sleep 永远对不齐）。持续检测五个信号：网络请求全部完成、图片全部解码、关键区域 canvas 已有像素内容、页面动画执行完毕（animationend/transitionend）、页面文本和布局连续两次快照一致——五信号全部就绪才截图。**闭环对账**：配表 N 条分支实跑覆盖 M 条，M < N 必须补跑或给出说明，不允许静默漏测。

### 报：报告 + 每账号汇总图 + 回归脚本

三件产物顺序固定：① 测试报告（核心交付物：测试概览、账号×数据展示矩阵、缺陷清单、未覆盖原因、结论）→ ② 每账号截图汇总图（grid 平铺按 PAGE_SORT 排列，标注账号典型数据特点与覆盖的 condition）→ ③ 自包含 UI 回归脚本（固化账号 + cookie + 每页预期，下次直接复跑，不再走配表/查表/找角色）。看板式美化报告和**截图画廊**（所有截图按页面分组平铺 HTML 画廊，点击放大、← → 切换；85 个分支一眼扫过，前端/产品/设计可直接用；回测时新旧画廊对比改动影响一目了然）是可选增强，不能替代①。

### 审：后端代码审查（独立诊断，补「配表+DB 查不出来」的缺陷）

前四阶段验不出「数据库到接口返回」这一段映射的问题：如 service 层漏写赋值 → 接口永远返回零值 → 配表分支永远命不中，但配表有兜底，页面看起来正常。做三件事：**字段映射比对**（entity → model → service 三层差集，找「定义了、取到了、但没赋值」）、**配表引用交叉验证**（condition 引用的每个字段确认后端有赋值路径）、**同类方法一致性检查**（结构相同的接口方法校验逻辑是否一致，揪越权隐患）。先全量扫可疑点，再拿真实 sample role_id 注入页面确认。独立于前四阶段，不阻塞主流程。

### field-mapping 说明书

后端源码在「一次性初始化」中把字段名、段位档位、模式枚举、DB 列映射、计算口径写进 `field-mapping.yjwj.mjs`，阶段 1~3 不再碰后端代码：阶段 1 靠它知道字段值域/分档规则才能算集合覆盖；阶段 2 靠它规定 DB 侧等效查法（condition 字段常是后端算出来的而非直接存列）才能采样出真实角色；阶段 3 靠它把接口返回值映射到区间和期望文案。

> 核心认知：年报看起来是 UI 测试，但真正决定测试质量的不是「点页面」，核心是**数据分析能力**——解析 condition、查 DB 枚举反查漏配、从真实玩家数据采样定位角色；UI 只是最后验证结论的那一层。

## 四、实践成果（永劫无间 D90 五周年年报）

| 执行线 | 结果 |
|--------|------|
| 接口测试（模式B） | 61 用例，51 通过 10 失败，83.6%；关键发现：错误码优先级（非活跃玩家返回 30010 对局数不足先于预期 30009 未看年报）、`/report-share` 缺 view_self 前置校验（未看年报可直接分享成功）、roleId 可作 share_code（后端同时支持 roleId 与 UUID）、空 share_code 未返回 20002 |
| UI 测试 | 20 用例（AUTO 8 + BIZ 4 + DATA 页面 5 + 移动端 3），19 通过 1 失败（BUG-1：pt4 宣发用户访问好友分享链接未被拦截），通过率 95%，双端 PC+移动，24 张截图 |
| 年报数据测试 | 20 账号 153 截图全通过；配表分支覆盖率：活跃版 13/13、回流版 4/4、宣发版 3/3（4 个高端位测试库无真实玩家）；缺陷 6 项：段位模式变量未填充（回流总结页 2012）、season_name 管道不生效显示原始日期、friend_list=null 但有 top_friend 时社交页整页漏渲染、宣发 promo3/4 文案为占位、四煞娱乐面板接口有数据但前端无渲染模板、**P0 字段映射遗漏 ent_liumangjie_win_rate 漏赋值 API 永远返回 0（六芒劫 2 条分支恒走错）** |
| 海外多语言 | 25 PASS / 1 SKIP / 204 截图 / 26 账号 / 5 并发；发现：翻页按钮与组队页显示 i18n key（report.viewMore、report.rankUp）、繁体宣发账号配表文案不对 |

## 五、提效收益（人工 vs skill 自动化，按流程对齐）

| 环节 | 人工测试 | skill 自动化 |
|------|---------|-------------|
| 配表分支解析 | 读 85 行 × 4 分钟 ≈ 5.7 小时 | 解析配表 + 集合覆盖算账号 ≈ 1 秒 |
| 构造测试账号 | 138 字段人工构造 ≈ 11.5 小时 | 定位角色 + 生成 cookie ≈ 几分钟 |
| 逐页核对/交互/图片扫查 | 每账号 16 页 ≈ 15 小时 | 并行多开浏览器 + 四层断言 ≈ 15~40 分钟 |
| 报告产出 | 靠笔记/截图手动整理 | 报告 + 汇总图自动拼接 ≈ 数十秒 |
| 配表数据检查 | 人工做不到 | 反查真实数据分布 ≈ 数十秒~几分钟 |
| 代码审查 | 138 字段逐个核对 ≈ 3.3 小时 | 拉代码扫 138 字段映射 ≈ 数十秒 |
| **合计** | ≈ 33.2 小时（≈ 4 天） | 全流程首次 ≈ 30~60 分钟 |

**测试时间提效 33~66 倍**。表面是 UI 点点点，核心价值在数据分析与造数过程。

## 六、边界与下一步

1. 动画效果、视觉细节仍需人工把关（数值过长无单位、配表少百分号、文案重叠等视觉问题 AI 识别不出，需人工看画廊）
2. 接入 CI/CD：当前 skill 手动触发，规划配表 MR 合入时自动 diff 变更的 condition、定位角色、跑 UI、产出增量报告
3. 架构可复用到其他游戏年报或非年报类「数据驱动展示」活动（战报、赛季总结）
