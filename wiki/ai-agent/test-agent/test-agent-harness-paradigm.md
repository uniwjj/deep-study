# AI 测试协作范式：分层与 Harness

云音乐在 SDD 研发流程中以测试分层为核心的自动化测试实践总结（王维恒、余成章分享）。总体思路一句话：**让 AI 负责理解与生成（概率），让 Harness 负责确定性，让人负责风险和关键判断**。

## 一、看过去：传统自动化如何运转（共建/复利/运营）

基于源码复盘某知名互联网公司大型资讯 App 的传统自动化体系，总结为三个词：

1. **共建** — 同一质量目标、不同专业分工：研发写单测/组件测试/提供业务原子能力；测试把这些能力串成 E2E 流程，沉淀公共步骤、公共用例和场景数据；框架统一提供 Mock、Checkpoint 和断言。研发和测试都通过代码完成测试，共用同一套自动化底座。
2. **复利** — 资产越丰富，新增测试越像搭积木：脚本 + 测试数据 + Checkpoint 重复组合和复用，新用例更快、更稳定，边际成本持续下降。
3. **运营** — 自动化不是一次建设而是长期运营：持续协作 → 资产有效 → 持续产生价值；投入一旦中断 → 资产劣化 → 恢复接近重构。

核心不是某个框架，而是**持续共建、复用和运营测试资产的能力**。AI Agent 带来的机会：按需求和代码变化自动生成、执行和维护用例、Mock 及检查点，显著降低长期维护成本。

AI 介入后，业界方向趋同（见 [[ai-test-industry-practices]]）：不只生码，还要对执行结果做校验、把失败闭环起来；测新由 agent 动态探测后固化为回归资产；**现在的壁垒不在生码，而在业务知识、环境数据、可信断言和工程闭环**。

## 二、测试左移：缩短交付路径，而不是去掉测试

- 传统串行交付：编码完成 → 提测 → QA 集中测试 → 问题退回 → 重新提测，摩擦和沟通成本高。
- 左移后的质量验证：需求与编码 → **开发 + Test Agent**（单元测试｜组件测试｜变更场景）→ 携带质量证据提测 → **QA 系统性验证**（跨系统链路｜高风险场景｜发布门禁）→ 发布。

按风险和系统跨度分层分工：

- **低风险、单模块需求**：开发掌握最完整的需求和代码上下文，倾向让开发基于 Test Agent 自主验证，产出质量结论。
- **高风险、跨系统需求**：没有单个开发能掌握全部上下文，由开发 + Test Agent 完成模块自测，**QA 负责系统性验证**、制定测试范围和质量标准、把关发布条件。
- 底线：无论项目大小，开发都需完成本模块自测；资金、权限和数据安全等高风险改动不能跳过专业验证。

## 三、测试分层 L1~L4

| 层级 | 验证对象 | 主要负责人 | 执行时机 | 主要目标 |
|------|---------|-----------|---------|---------|
| L1：单测 + Mock | 方法、函数、逻辑分支 | 开发 | 编码时、冒烟前 | 验证基础逻辑 |
| L2：组件测试 + Mock | 模块、接口、UI 组件 | 开发 | 编码时、冒烟前 | 验证局部模块 |
| L3：面向变更的自动化/半自动测试 | 本次需求涉及的业务链路 | 开发为主，测试"盖章" | 正式提测前 | 证明本次变更可交付 |
| L4：冒烟、回归、E2E | 跨模块、跨系统、完整链路 | 测试为主 | 提测后、发布前 | 识别系统和回归风险 |

- 层次越低：反馈越快、成本越低、开发责任越强；越高：场景越复杂、成本越高、测试判断越重要，L4 基本交给 QA。
- 四层模型解决两个问题：避免所有风险都堆到成本最高的 E2E 和回归阶段；明确不同问题由谁负责、在哪个阶段发现。
- 核心结论：**不追求所有场景都自动化，优先自动化高频、稳定、结果可判定的场景**。

## 四、Test Agent 工程化的四个关键问题

| 现象 | 技术本质 | 应对方式 |
|------|---------|---------|
| Agent 跳步骤、流程中断 | 上下文过大，流程只依赖自然语言约束 | 隔离 Test Agent，确定性步骤脚本化、Tool 化 |
| Token 消耗接近开发流程 | 每个环节重复携带大量上下文 | Skill 瘦身、阶段化上下文、稳定后使用低成本模型 |
| 生成代码不符合规则 | 测试规范只是会话中的弱约束 | **Spec First**，把测试设计和生码规范变成正式输入 |
| 用例生成后无法执行 | 缺少账号、环境、数据和 Mock 能力；脚本语法缺少自检 | 建设造数、环境准备和运行时适配能力；脚本预编译 |

## 五、Harness：AI 负责概率，Harness 负责确定性

职责拆分：Agent 理解需求、探索代码、生成候选方案（概率性）；Harness 掌握**流程权、状态权、验收权和恢复权**（流程｜状态｜门禁，有限恢复）；人负责关键业务判断和复杂失败的最终决策。真实运行与证据（环境｜数据｜执行；日志｜快照｜断言）失败后反馈回 Harness。

Harness 解决四件事：

1. **流程确定**：任务拆解、DAG 和状态机，明确执行顺序和完成条件
2. **输入确定**：以需求、用例和测试 Spec 限定测试范围、前置条件和验证目标
3. **结果确定**：测试代码必须经过机器校验、人工评审和真实执行
4. **失败收敛**：只允许有限重试和定向修复，疑似业务问题立即转人工

### 客户端与服务端两套方案

| 方向 | Harness 的主要控制对象 | 最终产物 |
|------|----------------------|---------|
| 客户端 | 生码流程、质量门禁、真实设备验收 | 可信测试资产 |
| 服务端 | 环境、动作、内部观测、断言和失败归因 | 有证据的质量结论 |

**客户端**：QA 流程使用单独 pipeline，与开发流程分开、除少数依赖节点外大部分并行；QA 流程 All in WebUI（见 [[mara-test-platform]]）；测试 spec first：用例 → 测试 spec → 测试生码 → 执行。Harness 三层控制：生成前有约束（需求+用例+Spec 限定范围）、生成后有验收（机器校验完整性/一致性/可执行性，关键业务判断由人确认）、交付前有实证（真实环境执行，携带日志、覆盖情况和测试报告）。工程收敛六项：Test Agent 与开发 Agent 会话隔离；确定性步骤脚本化/Tool 化；生码规则从会话提示词提升为正式 Spec；QA 操作路径统一收口 WebUI；补齐账号、测试数据、Mock 和环境准备能力；流程约束稳定后低成本模型可完成大部分标准化任务——**流程可靠性不再完全依赖模型能力**。

**服务端**：串行模式——开发完成后部署远端 → spec → 文本用例 → 脚本代码 → 执行。Harness 控制四环节：**执行前受控**（契约、环境、数据、状态隔离）→ **执行中可观测**（真实 HTTP/RPC/Bean 调用 + SQL/日志/Snapshot/Checkpoint 观察内部状态）→ **执行后可证明**（验证返回值、业务状态和副作用，保存步骤/快照/检查点）→ **失败后可收敛**（资产问题有限修复、业务问题转人工；定向修复/有限重试回环）。核心关切：运行环境是否正确、前置数据是否可信、返回成功后内部状态和业务副作用是否符合预期、失败来自测试资产/运行环境还是业务代码。

## 六、复利工程与下一步

复利建设核心思想：**测试代码也是需求交付的一部分**，保障测试代码稳定可靠运行需要四类沉淀：业务背景知识（生成合理用例）、业务代码知识（减少每次探索上下文，人工可介入注释和增强）、测试数据（支撑 Mock 业务场景）、业务原子能力（编排业务特定操作）。

下阶段三个方向（跨部门会上的认知转变）：

- **贴近研发 loop**：让开发把测试职能作为开发的一部分，与 SDD 结合，agent 闭环排查问题、调试、解决；缺的是 AI 在 runtime 的调试能力与流程串联。
- **复利工程**：业务知识和数据要业务自己沉淀，需要组织自上而下认可这套规范与数据沉淀方案。
- **分层次 e2e**：不追求全面 e2e 自动化（e2e 的脚本与断言生成有严重幻觉），改为分层 + 半自动化：Mock、执行步骤自动化，结果断言人 review（过程透明易懂，提升 review 效率）。只做步骤生成时成功率很高，难在让 AI「评价对还是不对」。
