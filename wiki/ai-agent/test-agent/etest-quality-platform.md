# Etest 质量保障平台（效率工程部）

效率工程部（秦龙分享）以 Etest 平台为底座、本地 Agent + Skill 的测试体系建设实践。是会前调研中**唯一进入「规模化应用」阶段的团队**。

## 架构与业务

服务对象：员工端（POPO 云协作、点餐）、职能线（HR）与营销业务——系统多、技术栈杂。组织：技术质量中心下设效能组 + 三个业务测试组。测试资产中心化沉淀到 Etest 平台并**开放 CLI 能力供 agent 调用**。

Etest 五层架构：

```
统一质量工作台（用例/执行/脚本维护）
→ Agent 接入与运行时治理层
→ Etest Skills + CLI 连接桥梁层
→ 工具执行层（接口/链路/流程编排）
→ 统一数据资产层
```

10+ 个 etest skill 产出，覆盖需求提测到准出、测试报告生成全阶段，支持一键安装。

## 三大亮点

1. **测试范式升级**：测试资产从「用例+报告」扩展到「自动化脚本+知识库」；知识库沉淀组件库与历史问题，Web 端 UI 自动化执行准确率较高
2. **跨域全链路串联**：订单→采购→财经（费控→核算→资金）长链路场景，一个场景调用其他域用例，实现本地 agent 全链路一致性验证
3. **知识库维护**：各域均沉淀本地知识库，对准确率提升有较大帮助；正在做知识库在线化，自动筛查冲突逻辑与历史错误逻辑

## 效能收益与痛点

- 收益：整体测试效率提升约 40%；新场景 Web 端 UI 自动化覆盖率约 80%；外包规模从 70+ 人优化至 40 人（8 月组织调整又合并入 10 人到 50 人），平台工具由正职 + 外包共同使用
- 痛点①：客户端自动化仍停留在回归阶段，脚本生成需人工大量介入（OCR+视觉）
- 痛点②：外包基础能力偏弱，AI 完成 80-90% 后「接下一步」的能力不足，复杂能力需正职先沉淀稳定再下放
- 痛点③：上下文压缩和幻觉——PRD 长上下文压缩导致专业名词丢失，需检测 + 脚本固定拆章节 + 责任拆分处理，类似问题需不断识别和调整

## 讨论要点（Q&A 摘要）

- **Web UI 用例执行**：基于纯自然语言描述执行（Deepseek 模型），但配套完备的组件库、页面导航与知识库（系统访问地址、可用账号、菜单层级、核心元素、组件定位操作）帮助定位；基于自然语言执行效率偏慢，过程和最终结果需人工校验
- **滞后反馈场景断言**（数据/资金类）：可用自然语言描述，但可指定调用 etest 某接口、查某类订单，或调外部脚本访问数据库——**确定性查询能力需独立提供**，复杂数据逻辑建议走脚本；接口参数组装靠 OA 标准化能力 + prompt 描述（生成时明确输入输出：金额 5、税率 1%，断言 0.05），断言在用例生成时全部生成好
- **表单数据来源**：生成时参考历史单据、拉历史代码库（本地 agent 甚至能直接访问数据库拿真实数据），再按本次需求约束调整；纯新场景看 PRD 描述
- **用例生成成功率 90%+ 的三支来源**：本地 harness 知识库全不全、历史知识够不够、本期 PRD 描述是否清晰有无冲突遗漏——**三支漏一个就是风险**。为此做了大量 SPEC 工作，并每周复盘用例生成未达标原因；纯新场景用能频繁反问、遍历分支的 skill（如 grillme、wayfinder），质量会高很多
- **脚本沉淀路线判断**：纯 AI 语义执行性能差（推荐并行晚上跑）、token 消耗多；「固定脚本 + 偏 AI 理解」的混合思路更好（知识更新导致的脚本更新交给 AI 改，成本低）。判断：浏览器端基本都能用脚本（canvas 与编码暴露节点有关）；Web 执行视觉用得不多，配组件库 + OCR 基本够；**建议新项目用自然语言方案，持续维护项目用「沉淀+脚本」；UI 回归应该做脚本，否则成本高**
