# 本体驱动知识工程

> 核心判断：企业 AI 的需求表面是应用问题，底层是**知识组织问题**。把大模型接到散乱知识上，只会放大散乱；先把知识变成"可定位、可约束、可追溯"的结构。**谁掌握企业语义层，谁才能把 Agent 从"会回答"推进到"会执行、能审计"。**

演讲来源：2026 Agent 大会「面向Agent的知识工程与本体语义构建论坛」，马金龙（启明致远），面向核电等强合规行业的智能办公场景。

## 01 企业 AI 面临知识困境

- 知识资产规模庞大，但分散在文档、业务系统、IM、邮件和个人经验中
- **首次检索成功率不足 40%，平均耗时 30 分钟以上**
- AI 需求集中在检索、合规审查、文档分类，本质都是知识底座缺失

**企业办公 AI 需求占比**：39.5% 智能检索（问答、查制度、找历史案例）、23.5% 合规审查（制度/合同/技术文档核对）、17.3% 文档分类整理（归档、标签、版本、专题库）。

**知识困境有三层**：

| 层 | 表现 |
|----|------|
| 找不到 | 知识散落在 DMS、EAM、邮件、制度库、项目盘，检索词和业务语义不一致 |
| 看不懂 | 同一设备/流程/条款多种叫法，文档块没有实体、关系、版本、适用范围 |
| 用不稳 | LLM 给出看似合理的答案，但缺少规则约束、来源证据和审批边界 |

专家退休与人员流动会进一步放大问题：经验不被编码，就无法被检索、继承和验证。

### 纯 RAG vs 本体增强生成

| 维度 | 标准 RAG | 本体增强生成 |
|------|---------|-------------|
| 检索 | 向量相似度返回文本块 | 先检索受控对象与关系边 |
| 版本 | 难区分当前有效版本与过时材料 | 带版本、适用范围、证据位置 |
| 约束 | 无法表达设备、人员、流程、条款之间的约束 | 用规则限制输出空间 |
| 审计 | 结果难以审计和复核 | 生成结果可追溯、可校验 |

## 02 本体驱动的三层架构

越往下越难复制，也越决定上限：

| 层 | 内容 | 定位 |
|----|------|------|
| 入口层 | AI 问答 / 搜索界面 / 办公助手 / 审查工作台 | 好做，容易同质化 |
| 中间件层 | LLM 编排 / RAG 框架 / Agent 调度 / 模型路由 / 权限 | 必争，工程复杂 |
| **知识工程本体层** | 领域本体 / 规则 / 证据库 / 版本基线 / 语义治理 | **壁垒，最稀缺** |

真正的壁垒不在界面，而在语义层和治理闭环。

### 六类本体：把办公知识拆成可治理对象

| 本体 | 内容 |
|------|------|
| 业务对象本体 | 设备、项目、合同、制度、会议、人员、组织 |
| 文档知识本体 | 文档、章节、条款、表格、图片、版本、来源 |
| 流程任务本体 | 审批、审查、维修、会议、工单、报告生成 |
| 规则约束本体 | 标准条款、合规规则、权限、适用范围、冲突条件 |
| 证据反馈本体 | 引用片段、审计日志、专家修订、评测样本 |
| 安全规则本体 | 国际国内标准，公司内部治理本体规则 |

（引用：GB/T 48000.3-2026 将本体界定为表达实体类型、关系、属性及其关联的模型；企业本体的关键是把"共同理解"工程化。）

### 五种核心关系：让知识从"资料库"变成"可推理网络"

| 关系 | 类型 | 示例 |
|------|------|------|
| 属于 | 对象归属 | 设备属于系统、文档属于项目、条款属于标准 |
| 演化 | 版本变更 | 设计态到竣工态、制度版本变更、会议决议闭环 |
| 适用 | 范围匹配 | 制度适用部门、手册适用设备、规则适用场景 |
| 约束 | 规则校验 | 安全等级约束备件、权限约束操作、版本约束答案 |
| 引用 | 证据追溯 | 报告引用标准、纪要引用决议、工单引用手册 |

> 关系不是"图谱好看"的边，而是 Agent 选择工具、检索证据、执行校验的语义路径。

### 融合策略：LLM+本体不是替代关系，而是双引擎协同

| 知识类型 | 方案 | 可信度 | 场景 |
|---------|------|--------|------|
| 核心知识 | 本体 + 规则 | >85% / 高可信 | 审查红线、条款适用、版本有效性、参数一致性 |
| 一般知识 | LLM + 本体约束 | 80-85% | 审查说明、问题归因、报告编写、跨文档摘要 |
| 辅助知识 | LLM 自由生成 | >70% | 润色、解释、格式转换、低风险问答 |

原则：**风险越高，越靠近本体与规则；表达越开放，越交给 LLM。**

### 检索策略：GraphRAG 把"多路召回"变成"证据链组合"

多路召回（向量召回找语义相近片段；关键词召回保留编号、术语、设备位号、条款号；图谱推理沿实体-关系-规则-证据追溯；规则校验过滤失效版本、权限越界、适用范围不符）→ 意图识别（识别文档类型、审查场景、目标条款）→ 图谱扩展（沿适用/引用/约束/演化关系找证据）→ 多路召回融合（向量、关键词、SPARQL/图路径融合）→ 规则过滤（版本、权限、适用范围、冲突条件）→ LLM 生成（问题清单、依据和修改建议）。

> 区别于纯 RAG：本体先限定对象、关系、版本和规则，LLM 只在可信证据包内组织答案。

### 六步建模法：把业务语言转成可执行语义

1. **场景定界**（任务与红线）：确定审查中的文档类型、审查任务和高风险规则
2. **术语归一**（标准词与别名）：标准词、同义词、别名、编码和业务口径
3. **实体建模**（对象与属性）：定义文档、条款、设备、参数、规则、证据等类型
4. **关系建模**（语义路径）：建立属于、适用、引用、约束、演化等核心关系
5. **规则建模**（约束与冲突）：SHACL/SWRL 表达必填、范围、冲突和继承规则
6. **评测迭代**（样本与反馈）：用审查样本持续评估召回、漏检、误报和可追溯性

建模目标：不是画概念图，而是让知识能被**检索、校验、推理、生成和审计**。

### 本体元模型：类、属性、个体、公理构成领域语法

- **类 Class**：文档、条款、设备、规则、问题、证据
- **个体 Individual**：某份制度、某个条款、某台设备、某条问题
- **对象属性**：适用、引用、约束、属于、影响
- **数据属性**：版本号、生效日期、参数值、风险等级
- **公理 Axiom**：子类、等价、互斥、继承、取值约束

（OWL 2 把本体表达为类、属性、个体和公理；这些元素对应璟审中的对象、关系、证据与审查规则。）

### 知识工程评测：用指标证明本体建模真的提升审查能力

| 维度 | 指标 |
|------|------|
| 本体质量 | 概念覆盖率、关系完整率、同义词归一率 |
| 检索质量 | 首检成功率、证据召回率、路径命中率 |
| 审查质量 | 漏检率、误报率、规则命中率、人工采纳率 |
| 可追溯性 | 原文定位率、条款依据完整率、版本有效率 |
| 迭代效率 | 规则更新周期、专家修订闭环、样本沉淀量 |
| 实施效率 | 知识工程的交付和实施周期 |

评测闭环让本体不是静态资产，而是随审查问题、专家反馈和标准更新持续演化的知识系统。

## 03 知识工程本体实现路径

以终为始：选择高价值、高频、可评测的业务闭环；**最小可行本体 MVO**——先跑通一个场景，再扩展对象和关系；LLM 辅助建模降低人力成本约 30%，但治理权仍在业务专家。

### 两周可跑通一个可评测、可上线的 MVO

| 阶段 | 周期 | 内容 |
|------|------|------|
| 选规则 | D1–2 | 选择高频审查场景和红线规则 |
| 抽文档 | D3–5 | 标准、制度与样本（由璟疏解析） |
| 入本体 | D6–8 | 实体抽取、关系对齐、证据挂接 |
| 写校验 | D9–10 | 适用范围、版本、阈值、冲突规则 |
| 做评测 | D11–12 | 漏检率、误报率、可追溯性 |
| 上线 | D13–14 | 璟审工作台与专家反馈闭环 |

先跑通一个闭环，再扩展对象、关系和规则。

### LLM 辅助本体构建能降本，但不能替代治理机制

| LLM 适合做 | 业务专家必须做 |
|-----------|---------------|
| 从文档中抽取候选实体、属性、关系 | 确认核心概念和边界 |
| 根据表结构生成 Schema Mapping 建议 | 批准规则、阈值和适用范围 |
| 发现同义词、别名、版本差异 | 评审高风险输出 |
| 生成规则草案和评测问题 | 维护变更流程和责任机制 |

经验目标：LLM 辅助本体构建可**降低人力成本约 30%**，同时提升知识工程迭代速度。

### 生产化的分水岭是持续评测：常见五大坑

| # | 坑 | 后果 |
|---|----|------|
| 1 | 只建向量库，不建实体、关系、版本和证据 | 答案难复核 |
| 2 | 忽略治理边界（权限、有效期、适用范围） | 办公 Agent 越权或引用失效材料 |
| 3 | 缺少反馈入口 | 模型错误无法沉淀为规则和样本 |
| 4 | 只做应用界面，不建设底层语义资产 | 后续场景复用成本很高 |
| 5 | 追求大而全 | 迟迟无法进入业务闭环 |

评测指标按阶段：检索（首检成功率｜证据召回率｜平均耗时）、生成（事实一致性｜引用完整性｜格式合规）、规则（冲突检出率｜误报率｜版本过滤率）、运营（人工采纳率｜闭环时长｜知识更新周期）。**没有评测，Agent 只能停留在"看起来能用"；有评测，知识工程才能持续改进。**

## 04 智能办公落地应用

主场景：**璟审**（本体、规则和证据链落到文档审查闭环）；次场景：**璟疏**（知识工程底座增强会议纪要生成）；扩展场景：**璟序**（文档结构化与知识入库、术语治理）。

### 应用一：璟审——智能文件审查

- 产品需求：文档必须具备编号、版本、生效日期、适用范围；参数值必须有单位、来源、取值范围和证据位置；条款适用设备类型，问题必须回指原文证据；冲突规则（如低等级备件不得替代高安全等级设备部件）
- 技术路径：规则库（标准条款、企业制度）+ 审查引擎（格式、语义合规、一致性）+ 知识工程（实体、关系、版本、影响链）+ 审查工作台（定位、确认、报告、审计）
- 验证报告：输出违规节点、违规属性、规则 ID 和修复建议

**规则先验 + 图谱证据 + 人工确认，让审查结果可定位、可解释、可审计。**

璟审八大能力：数据接入（API/数据库/文件）、基础审查（文本/格式/完整性）、图谱应用（查询/一致性/治理）、对比分析（版本对比/差异总结）、文档解析（多格式/表格/多模态）、规则知识（规则引擎/词汇/行标）、智能审查（语义/合规/风险）、交互工作台（操作/修复/报告）。产品架构四大层：1. 文档智能审查、2. 规则管理中心、3. 智能质检引擎、4. 平台支撑层（用户管理、权限管理、内容源管理、知识库管理、审计日志、统计分析）。**面向核电等强合规行业**，支撑文档自动审查、标准驱动、质文档一致性分析与可审计闭环。

（演示截图：基于本体的规则抽取——从文档抽取规则（如"维修程序编制-自动抽取"、"维修程序编码必须符合 11 位结构"）；审查问题定位——问题列表按严重程度（高/中/低）与问题类型分类；问题定位与证据回指——每条违规问题回指上游文件条款原文与修改建议，形成可审计结果。）

### 应用二：璟疏——智能会议纪要

- **声纹识别补齐"谁在说"**，联动企业组织架构进行声纹注册，组织信息补齐"以什么角色说"——更清晰参会人的角色
- **自定义会议模板**：系统内置 + 个人模板，按会议分类（通用、项目周会、客户沟通会等）管理，模板包含会议基本信息、背景目标、议题讨论、关键决策、待办事项等模块（如通用模板 7 个模块、项目周会模板 20+ 模块），已启用/已禁用管理
- **融合原文、材料与组织信息生成可信纪要**：会议纪要含会议主题、时间、参会人、总结、待办事项、智能章节（带时间戳）、会议内容分点阐述，标注"智能会议纪要由 AI 生成，可能不准确，请谨慎甄别后使用"

### 应用三：璟序——把解析、治理与生成连成知识入库链路

解析（PDF / Word / 扫描件）→ 入库（按业务语义拆解）→ 治理（本体对齐 / 术语归一）→ 生成（跨文档追溯）。文档不再只是文件：解析后形成可定位的章节与条款；治理后对齐企业术语与本体，生成时可追溯来源。

（演示截图：文档结构本体构建及辅助生成——文件结构化系统编辑器，章节级解析（如 12/12 章节完成）、知识检索、规则治理、AI 建议（置信度 30%-70%，建议人工审核修改）、AI 重写、跨文档追溯。）

## 05 总结与展望

- 本体为企业 AI 提供**领域语法、约束边界和证据链**；LLM 负责理解与生成，本体负责确定性、可追溯和可治理
- **三句话带走**：不是先做聊天框（先把知识变成可定位、可约束、可追溯的对象网络）；不是让 LLM 替代专家（让 LLM 在专家定义的本体、规则和证据范围内高效协作）；不是一次性建库（从高价值场景小步快跑，持续治理，逐步形成企业 AI 壁垒）

### 底层知识的组织方式，决定 AI 应用的天花板

三层定位不变（入口层：好做·同质化；中间件层：必争·红海；知识工程·知识图谱·本体层：壁垒·最稀缺）。标准参考：**ISO 15926（4D 时空泛化）+ IAEA DK-PIM + S1000D/GJB6600 + OWL/SHACL/SWRL**。核心展望：谁掌握语义层，谁掌握下一代工业 AI。

### Palantir 证明：本体优先战略是 AI 制胜关键

- **385B+ TAM 市场规模、5% YoY 营收增长率（2026 年 Q1）**（Wolfe Research）
- Google Cloud Gemini + AIP：**BigQuery ↔ Ontology 双向语义打通**
- **模型无关架构**：xAI / Claude / Google 均可接入

三项核心启示：
1. **OAG（本体增强生成）替代标准 RAG，成为企业 AI 新范式**
2. **Delta + Echo 双团队 FDE 模型**：工程师嵌入客户内部，从运营真实中提炼产品
3. **本体 = 知识图谱进化版（名词+动词）**：静态知识 → 动态决策执行
