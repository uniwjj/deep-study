# WorkBuddy Agent 产品设计

> 作者：Anne（腾讯 WorkBuddy 策略产品经理），2026年7月
> 核心命题：模型够强就行？Agent 要可用，还得靠模型之外的系统能力。

## 产品哲学

一个常见判断是"模型够强，剩下交给提示词"。但把 Agent 做成能在生产环境稳定完成任务的产品后，会发现模型只承担其中一部分。**工具接入、上下文组织、权限边界、结果验证、反馈纠正和跨会话延续**，都会直接影响产品是否可靠。

从产品运行机制看，一次模型调用可以类比为一个函数：

```
输出 = 模型(系统提示词 + 工具 + 会话历史 + 其他上下文 + 用户指令)
```

这个抽象包含**两条约束**，决定了上层所有工程的存在理由：

1. **模型是无状态的** — 模型不会自动保留上一次调用的内容。但产品可以有状态。对话历史、Memory、数据库由产品在模型外部保存，需要时再注入。WorkBuddy 的对话连续性、记忆和工作进度，都由产品侧维护状态再注入实现。
2. **模型的知识截止到训练日期** — 训练之后发生的事，模型默认不掌握。需要先用工具查询再放进上下文。

也就是说：**模型本身提供语言理解、推理和生成能力；实时信息查询、文件读写、数据库操作等外部动作，都不是模型自带的能力。** 产品需要在模型外接入工具和执行环境。

### 模型训练三阶段（产品视角）

| 阶段 | 做什么 | 产出 |
|------|--------|------|
| 预训练（Pre-training） | 在海量文本上"根据前文预测下一个 token" | 习得语言、世界知识和部分推理能力 |
| 后训练（Post-training） | 用问答、工具调用、安全边界等数据训练 | 能听指令的助手 |
| 偏好优化与强化学习（RL） | 面对多个候选回答时，用人类反馈提高选中更优选项的概率 | 收敛到更优的执行路径 |

## 四大基础概念

### 工具调用（Function Call / Tool Call）

工具调用是模型与外部系统之间的结构化协议：**模型负责生成调用请求，Agent 负责执行**。

完整流程：
1. 产品把可用工具的名称、用途和参数 Schema 提供给模型
2. 模型根据用户目标，输出结构化的调用请求
3. Agent 校验参数、检查权限，执行 API、脚本或本地函数
4. Agent 把执行结果作为 tool result 放回上下文
5. 模型读取结果，决定直接回答还是继续调用其他工具

**关键要点：持有 API Key、发起请求、修改数据的是 Agent，不是模型。** 权限、审批、参数校验和审计日志都必须由模型外部的工程机制执行。

### 模型上下文协议（MCP）

MCP（Model Context Protocol）是 Anthropic 在 2024 年底发布的开放协议，用统一方式连接 AI 应用和外部数据源/工具。

MCP Server 向 Agent 提供**三种原语**，关键差异在于**谁来驱动**：

| 原语 | 驱动方 | 说明 |
|------|--------|------|
| Resources（资源） | 应用/Agent | 有 URI 标识的只读内容（文件、数据库记录、实时数据），由 Agent 决定何时读取注入 |
| Tools（工具） | 模型 | 模型在推理时自行决定是否调用，结果回流进上下文 |
| Prompts（提示模板） | 用户 | 用户主动点选（如斜杠命令）触发，模板内部可引用 resource |

三种原语说明，MCP 处理的不是单一的"工具调用"，而是 Agent 与外部系统之间的**信息、动作和提示模板如何被组织和传递**。

2026 年发布的官方扩展 **MCP Apps** 允许工具返回可直接渲染在对话中的交互式 UI（看板、图表、表单、确认界面），面向模型的摘要进上下文，面向用户的界面数据直接交给 UI 渲染。

运行结构上，MCP 有三个角色：承载 Agent 的产品（如 WorkBuddy）、MCP Client、MCP Server。MCP 统一的是连接协议，Server 背后仍可以是 REST、数据库、SDK。

**MCP Server 关键设计原则：按用户意图组织工具，不照搬底层 API。** 例如"创建 Issue"可能涉及四个底层接口，但对 Agent 只暴露一个 `create_issue` 工具。

### Skill

有了 MCP 和 Tool 后，真实任务通常不是调用一次工具就结束。**Tool 负责"一个动作"，Skill 负责"一类任务的做法"。** Skill 把经过验证的工作方法保存下来，包含说明、步骤、脚本、命令和判断标准。

一个完整的 Skill 包含：
- 适用场景
- 流程步骤（含失败分支）
- 完成标准
- 所需的工具和规则引用

**一句话区分：MCP 解决"外部系统怎么接入"，Skill 解决"这类任务应该怎么做"。** 两者可以组合——一个"发周报"Skill 可能同时调用腾讯文档 MCP、知识库 MCP 和本地脚本。

### Plugin

Plugin 解决"**能力组合如何安装和分发**"的问题。它把 MCP（连接外部系统）、Skills（任务流程）、Rules（规范约束）、Hooks（自动化检查）、Assets/Templates（模板资源）组合成可安装、可分发的单位。

```
Plugin: team-dev-workflow
├─ MCP：读写 Issue、MR、构建结果和内部文档
├─ Skills：/issue-start、/create-pr、/debug-ci、/release
├─ Rules：分支、Commit、安全、架构规范
├─ Hooks：编辑后 lint，提交前测试，发布前审批
└─ Assets/Templates：PR 模板、发布说明、架构图
```

**注意：MCP 是跨产品协议，Plugin 是产品层的打包概念。** 不同 Agent 产品对 Plugin 的定义可以不同。

### 四概念关系总表

| 概念 | 核心问题 | 主要消费者 | 典型内容 |
|------|----------|-----------|---------|
| 工具调用 | 模型怎么请求执行动作？ | 模型 + Agent | 名称、描述、Schema、调用结果 |
| MCP | 外部系统怎么标准化接入？ | Agent / Server | Tools、Resources、Prompts |
| Skill | 一类任务按什么方法做？ | Agent | 流程、约束、脚本、验收标准 |
| Plugin | 怎么安装和分发一组能力？ | 用户/团队/产品 | MCP、Skills、Rules、模板 |

### 外接能力形态选择

设计外接能力时，不能只问"能不能接进来"，还要判断它更适合哪种产品形态：

| 需求 | 优先形态 | 原因 |
|------|---------|------|
| 稳定的底层操作（读文件、执行命令） | 内置 Tool | 延迟低、权限和 UX 可深度集成 |
| 外部系统（文档、网盘等） | Skill/MCP/Plugin | 服务端集中维护，能力可标准化复用 |
| 团队高频稳定工作流程 | Skill | 沉淀步骤、判断标准与失败处理 |
| 需同时装连接、流程、规则和 Hook | Plugin | 作为组合与分发单位 |

## 一次完整任务的信息流

以"调研 OpenAI、Anthropic、LangChain 在 Harness Engineering 上的实践，输出带引用的大纲"为例，WorkBuddy 的执行流程：

1. **检查已有资料** — 先查看当前 Workspace 是否已有相关资料、草稿、PDF、书签
2. **读取 Memory** — 读取用户偏好的表达方式、文章结构等记忆
3. **查找 Skill 和规则** — 调研类 Skill 要求拆分对象、优先一手资料、记录来源
4. **连接内部数据源** — 结合产品架构文档、常见问题等内部资料
5. **拆分任务给 Sub-agent** — OpenAI、Anthropic、LangChain 分别交给不同 Sub-agent 并行调研
6. **Sub-agent 返回结果** — 返回结论、证据、来源和适用范围
7. **主 Agent 汇总并补齐缺口** — 合并材料、去重、识别冲突
8. **生成大纲并保存状态** — 记录资料来源、未解决问题和下一步建议

整个过程是多轮的 **ReAct 循环**（Reasoning-Acting）："判断—行动—观察"。每次观察到的结果都被放进模型上下文，**主上下文长度逐渐增大**，因此必须进行上下文管理。

## Memory 系统设计

> Memory 解决的是"重复交代背景"的问题。模型本身没有长期记忆，产品要做的是从历史交互中提取少量可信信息。

### 五类长期记忆

WorkBuddy 将长期记忆分为五类（均属于陈述性记忆）：

| 类型 | 存什么 | 系统作用 | 示例 |
|------|--------|---------|------|
| 稳定事实 | 去情境化的稳定事实、长期偏好、已确认的默认假设 | 长期推理前提，减少重复获取用户基础信息 | 用户所在城市、常用工作语言 |
| 用户知识背景 | 专业背景、知识水平和熟悉领域 | 调节解释深度和术语密度，不改变事实结论 | 用户熟悉 Context Engineering |
| 行为信号 | 从多次真实交互观察到的稳定使用模式 | 交互策略的调节信号 | 回答前先查看当前工作空间 |
| 表达偏好 | 对表达方式的稳定偏好 | 控制"怎么说"，不影响"事实是什么" | 先给结论、减少空话 |
| 会话延续信息 | 当前会话中有价值的目标、决策、进度、未完成项 | 帮助延续讨论和任务 | 已完成什么、下一步做什么 |

### 为什么程序性记忆不进入长期记忆

以上五类均属于**陈述性记忆（Declarative Memory）**——记录"用户是谁、了解什么、发生过什么"，提供的是推理前提，不直接规定 Agent 该怎么做事。

**程序性记忆（Procedural Memory）**记录"做事方法"。WorkBuddy 没有将其纳入长期记忆，原因：

- 局部经验可能被误升为通用策略（一次任务有效的步骤，换个项目未必成立）
- 干扰模型推理，可能不再根据当前证据选路径
- 隐性改写 Agent 行为，缺少版本、评测、审批和回滚
- 缺少稳定的奖励信号和 Eval 时，系统难以判断是在改进还是积累偏见

**WorkBuddy 的选择：用户事实和历史状态放进 Memory，经过验证的工作方法保存为 Skill**（Skill 可版本化、可评审、可测试、可回滚、按需加载）。

### 记忆作用域分层

| 层级 | 示例 | 解决问题 | 典型失效方式 |
|------|------|---------|-------------|
| 当前轮临时上下文 | 刚选中的代码、本次上传的文件 | 理解当前一步 | 任务结束即失效 |
| 会话/Thread 记忆 | 做到哪一步、哪些工具已调用 | 让多轮对话连续 | Thread 结束后归档 |
| 项目/Workspace 记忆 | 架构约定、活跃计划、已有决策 | 让 Agent 在场景里接着做 | 项目变更或决策替换 |
| 用户级记忆 | 长期表达偏好、职业背景 | 减少反复自我介绍 | 用户修改、撤销或降权 |
| 团队/组织记忆 | 团队流程、术语、组织边界 | 促进多人与多 Agent 协作 | 权限变更、制度更新 |

记忆注入分阶段：冷启动时注入少量高置信的摘要 → 请求理解时激活候选 memory cards → 执行中需要证据时回查原始会话 → 任务收尾时提取候选记忆并做去重、冲突检查和作用域判定。

## Harness 五层架构

WorkBuddy 将 Harness 定义为一个**控制系统**：Agent 行动前，系统通过**前馈（Feedforward）**提供目标、规则、环境和可用能力；Agent 行动后，系统通过**反馈传感器（Feedback sensors）**观察结果，并把错误和修正信息返回给 Agent。

> 前馈提高第一次就做对的概率，反馈让 Agent 在问题进入人工审查前先自我纠正。

### 三类能力（从词源出发）

| 能力 | 含义 | Agent 对应 |
|------|------|-----------|
| 驾驭（Steer） | 控制执行方向、速度和停止时机 | System Prompt/规则文件、Skills、Task/Todo、自我纠正提示 |
| 约束（Constrain） | 防止执行超出安全范围 | 权限边界、Sandbox、Approval Gate、Allowlist/Denylist、测试验证、Rollback、Audit Log |
| 整合（Integrate） | 把各项能力配齐并协同 | 执行能力（tools/MCP/browser/filesystem）、状态承载（memory/logs）、协作机制（subagents/hooks/connectors）、自动化（CI/定时任务） |

### 计算型 vs 推断型控制

| 类型 | 执行方式 | 优点 | 缺点 | 示例 |
|------|---------|------|------|------|
| 计算型 | 确定性程序执行 | 快、便宜、可重复 | 只能覆盖可写规则的问题 | LSP、类型检查、linter、单元测试 |
| 推断型 | 模型语义判断 | 覆盖"是否过度设计"等难以规则化的问题 | 更慢、更贵、更不确定 | Review Agent、架构审查、AI judge |

**WorkBuddy 原则：能用计算型信号解决的，优先交给确定性程序；需要语义判断的，再交给审查 Agent。**

### 五层结构

| 层 | 职责 | 核心内容 |
|----|------|---------|
| **1. 运行环境层** | Agent 在哪里执行 | 文件系统、Shell/Bash、Sandbox、Browser、MCP/Connectors、权限边界/Approval Gate、Allowlist/Denylist |
| **2. 引导层（Feedforward）** | Agent 开始前掌握什么 | 项目上下文、环境上下文、规则与风格、工具使用规则、Skills、上下文结构与 Prompt Cache |
| **3. 反馈层（Feedback）** | Agent 执行后如何获知错误 | 工具结果含可纠正信息、编辑前时间戳校验、外部验证信号回传（lint/类型检查/测试/构建）、Audit Log |
| **4. 编排层** | 多个能力如何组织 | 渐进式加载、意图识别和路由、多模型路由、Teams 多 Agent 协作、并行工具调用 |
| **5. 迭代层** | Harness 自身如何持续调整 | 随模型能力精简上下文、根据新问题增加约束、根据重复反馈增加机制（需证据支撑） |

### 使用者视角的四类组件

| 组件 | 作用 | WorkBuddy 实践 |
|------|------|---------------|
| 上下文工程 | 让 Agent 获得任务所需信息 | 分层规则文件、OpenSpec、Skills、Slash 命令 |
| 架构约束 | 把规则变成可执行检查 | 本地检查、Git Hooks、CI 门禁、审查 Agent |
| 反馈循环 | 把验证结果返回给 Agent | Post-edit checkpoint、本地检查与 CI 结果、/team:mr 工作流 |
| 熵管理 | 处理规则/代码/运行状态的漂移 | 周期性扫描 WORKBUDDY.md 一致性、重复实现、失效文档、过期依赖 |

## Loop Engineering

Loop Engineering 是近期出现的工程表达，目前还没有统一定义。前面几层关注"一次任务怎么做好"，Loop 关注 Agent 如何被触发、连续执行、验证结果、记录进度并再次运行。

### 四层工程体系

| 层次 | 核心问题 | 简单例子 |
|------|---------|---------|
| Prompt Engineering | 本次请求应如何表达？ | 写清目标、格式和约束 |
| Context Engineering | 这一次决策前，模型该看什么？ | 加载相关文件、工具、历史和记忆 |
| Harness Engineering | Agent 如何被引导、约束、观测、验证和纠正？ | 规则、沙箱、审批、测试、日志、编排 |
| Loop Engineering | 任务如何被触发、流转、验收、继续与停止？ | 定时任务、工作树、子 Agent、记忆、反馈闭环 |

> Harness 定义 Agent 的环境、权限、反馈和纠正机制；Loop 定义任务的触发、流转、重试和停止条件。

一个可用的 Loop 至少需要：**触发器、独立执行环境、Skills、Tools/Connectors/MCP、Sub-agents、Memory/Durable Artifacts、Sensors/Evals、Stop Conditions/Budget**。

**Goal ≠ Loop**：Goal 只定义"要去哪里"和"还剩什么"，Loop 还需要触发器、执行环境、工具、验证信号和停止条件。

## 四个待解决问题

### 1. 功能和业务正确性的验证缺口

目前的 Harness 实践主要讨论代码质量问题，对功能和业务正确性的验证讨论较少。四个原因：
- 需求本身很难完整说明（功能组合后的行为常常未被 PRD 覆盖）
- 同一个 Agent 既写实现又写测试，理解偏差会同时进两边
- 部分业务正确性缺少可计算的判定标准
- 业务错误的成本可能很高（资金损失、合规问题）

**自治度上限随风险提高而降低：**

| 场景 | AI 自治度上限 |
|------|-------------|
| 一次性脚本、内部工具 | 高 |
| 公开 API、跨系统改动 | 中 |
| 核心业务逻辑（支付、风控、订单） | 低 |

判断一项工作是否适合交给 AI 的四个问题：有没有明确的完成标准？结果能不能验证？失败是否容易发现、可回滚、代价可控？任务是否重复发生、值得为它建 Harness？

### 2. 代码库的 Harnessability 决定建设难度

老系统更难建 Harness 的原因：Harness 依赖清晰系统结构、大量历史违例降低规则有效性、高复杂度影响 Agent 理解、缺少可观测性信号。

更可行的做法：老系统先处理循环依赖和模块边界 → 补齐关键链路的测试/日志/指标/看板 → 再加 Harness → 先约束新增和修改部分 → 再逐步处理存量。

### 3. 案例有适用边界

目前主要案例来自模型厂商和框架团队，实验条件和业务验证方式并不完全公开。Harness 需要和具体代码库、技术栈、团队约定一起设计，很难把某一套模板直接搬到所有系统。

### 4. Harness 需要持续投入

OpenAI 实验从空仓库到 100 万行代码用了 5 个月，文章明确说："this isn't something you can jump into for quick results." 工程严谨度从代码编写本身，部分转移到环境、反馈回路和控制系统的设计上。

## 关键洞察

- **模型负责推理，Agent 负责执行** — 持有 API Key、修改数据的是 Agent，不是模型
- **System Prompt 只能引导，不能强制** — 权限校验、Sandbox、Approval Gate、审计仍由模型外部系统执行
- **记忆和 Skill 的边界** — 用户事实进 Memory，经过验证的工作方法保存为 Skill（可版本化、可评审、可回滚）
- **Harness 是控制系统，不是一次性配置** — 前馈提高首次正确率，反馈让 Agent 自我纠正，两者缺一不可
- **人能做的事和 AI 能做的事，边界在于可验证性**
