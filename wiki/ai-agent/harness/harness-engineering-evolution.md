# Harness 工程演进与落地实践

> 来源：2026 Agent 大会「Harness Engineering Agent执行与控制工程论坛」演讲《Harness 的工程演进和落地实践——从系统能力到企业级生产闭环》（PDF 题头含 DataFun 超级智能体系统架构峰会品牌），讲者艾长青。

## 核心论点

> 企业真正要建设的，不是更聪明的模型，而是可执行、可验证、可治理的智能体运行时。

真正的难点不在模型够不够强，而在工程闭环是否成立。

## 范式演进：从 Prompt 到 Harness

### AI 的演进：从交互到执行

| 阶段 | 能力 | 典型形态 |
|------|------|---------|
| 01 替代搜索 | 直接给答案 | Chatbot |
| 02 辅助工作 | 帮我写、改、解释 | Copilot |
| 03 解决任务 | 拆解、执行、交付 | Agent |
| 04 承担完整流程 | 跨工具持续推进 | Agent System |

技术演进的本质是能力边界的扩展：从生成文本，到调用工具，到管理状态。

### 四阶段演进

1. **Prompt**：表达意图——定义角色、任务、格式与约束
2. **Context**：注入知识——连接文档、数据与代码资产
3. **Tool / MCP**：获得行动——调用 API、工具与执行环境
4. **Harness**：形成闭环——整合状态、编排验证与治理

> 从"人写好提示词"，到系统让 Agent 可执行、可验证、可治理。

### Harness 才是大模型时代的真正胜负手

**① 基准测评实证：同模型换脚手架，分数成倍跃升**

| 基准 | 案例 | 数据 |
|------|------|------|
| SWE-bench | Particula | 42% → 78%，仅改脚手架即翻倍；弱模型+好脚手架反超旗舰 |
| Terminal-Bench 2.0 | LangChain | 52.8% → 66.5%，固定 GPT-5.2-Codex，使用更好的 harness 排名 Top30→Top5 |
| BrowseComp 智能体搜索 | Anthropic | 84.0% → 86.8%，固定 Opus 4.6，加装多智能体 Harness 后分数再提升 |
| 行业综述《Agent Harness Survey》 | — | 代码编辑任务成功率能飙升 20%+，辅以 Harness 防错机制 |

**② 落地实战案例：构建 2D 复古游戏（单代理 Solo vs 完整 Harness）**

| 对比维度 | 单代理 Solo | 完整 Harness |
|---------|-----------|-------------|
| 执行时间 | 约 20 分钟 | 约 6 小时 |
| API 成本 | $9 | $200 |
| 任务拆解 | 1 句提示直接做 | 16 功能 / 10 Sprint |
| 核心可玩性 | ✕ 实体无响应，游戏是坏的 | ✓ 可移动实体、真正可玩 |

> 同一模型，仅优化外围"运行脚手架"，性能即可成倍跃升。范式从"换模型"转向 Harness 工程。

### Harness：从能力调用到生产闭环（整车类比）

Model = 发动机，Harness = 整车系统周边；只有模型，Agent 无法稳定进入生产。**Agent = Model + Harness**：

| 部件 | 对应能力 |
|------|---------|
| 导航 | Context / Memory |
| 方向盘 | Prompt / Spec |
| 传动 | Tool / MCP |
| 刹车 | Policy / Permission |
| 仪表盘 | Trace / Observability |

Harness 的价值：把模型能力放进可行动、可观察、可反馈、可治理的运行系统。

## 落地挑战：八大工程难题拆解

> 统计：70%~95% 的 Agent 在生产环境中遭遇失败（Fiddler AI）。Demo 中表现完美，但进入多步骤、多系统的业务流程后，任务状态、上下文可信度、工具安全、结果验证每一项都会暴露问题。

业务目标到可执行结果的四个环节：**目标定义**（澄清目标、拆解任务、定义验收标准）→ **信息准备**（收集数据、对齐口径、权限过滤）→ **执行推进**（工具调用、状态追踪、人工协同）→ **验证交付**（质量验证、结果复用、经验沉淀）。每个环节都是工程难题，哪个没做好都无法达成业务目标——失败不是大模型不够聪明。

### 问题一：任务链路失控

- **后果**：任务中断导致无限重试，进度丢失无法完成任务，还烧掉高额账单（如 Agent 处理长周期文档任务中断后从头开始）
- **原因**：大模型是无状态的，一旦会话中断上下文即刻丢失（不是上下文窗口不够大）
- **解法：引入外部状态或存档机制**——状态定义机制（结构化定义当前进度、版本与上下文边界）、存储解绑策略（会话状态从模型上下文剥离至外部文件）、历史信息管理（一个任务多次提问、一次提问多次调用均作为历史信息喂给 LLM）、摘要总结（上下文过长时生成摘要并保存当前状态和处理进度）
- 必须像玩游戏一样自动存档，确保中断后能从断点恢复，而不是重开一局

### 问题二：上下文失真

- **后果**：2024 年因 AI 幻觉和错误决策，企业损失近 700 亿（案例：使用过期的设备维护手册导致生产线停机）
- **原因**：RAG 的错误认知——喂给 AI 的数据过多，可能发生"中间丢失"
- **解法：建立严格的知识边界与压缩策略**——知识边界划定（哪些数据可用、过期或需权限隔离）、来源追踪（关键结论必须附带数据来源与时效）、输入质量校验（格式/完整性/一致性结构化校验，拒绝低质量输入进入推理链）、压缩策略（策略压缩、语义与全局重建，长时间调用而不超最大上下文）
- 企业级应用准确性不可妥协，必须将"自由发散"变成"基于受控知识库的开卷考试"

### 问题三：工具调用风险

- **后果**：PocketOS 公司使用 Agent 排查问题，因错误调用 API 引发删库跑路的灾难
- **原因**：行动与验证脱节，赋予极高 API 权限却没有建立责任边界；目标明确但没有考虑误操作后果
- **解法：建立严格的工具治理闭环与权限沙箱**——能力与风险分级（明确工具能力边界、严格划分风险等级）、沙箱机制（隔离沙箱中验证高危工具调用结果）、人工审批（高风险操作强制拦截，遵循 Deny→Ask→Allow）、执行审计追踪（完整记录工具调用参数与结果，建立责任链）
- 提示词随时可能被覆盖，必须在执行层建立物理隔离，确保模型发疯也无法破坏

### 问题四：结果难信任

- **后果**：金融场景，Agent 生成审计报告错误引用法规条款，导致监管罚款
- **原因**：Agent 不懂装懂；验证机制缺失，人类核对认知负担太重
- **解法：构建多层次的自动化验证流水线**——确定性规则校验（输出前自动校验数值、格式与合规性规则）、权威事实比对（关键事实与企业内部权威数据源交叉比对）、独立评估打分（独立模型或 LLM-as-Judge 打分）、门禁拦截（未通过自动化证据链验证的结果严禁进入下游）
- 把质量检查变成机器自动执行的卡点，提供自动化证据链，人类才能放心信任

### 问题五：生产不可观测

- **后果**：Agent 自动化做营销方案，运行一夜发现没任何产出（原因：API 格式变化导致不断重试）
- **原因**：Agent 往往是逻辑上的失败，传统监控失效；缺乏针对推理过程和工具调用的追踪机制
- **解法：建立完整轨迹的细粒度可观测体系**——推理路径追踪（细粒度记录每步推理决策与分岔点）、工具调用串联（分散的工具调用输入输出串联为完整调用链）、实时状态看板（异常行为触发自动干预）、逻辑级根因复盘（基于完整轨迹实现逻辑级错误定位与优化）
- 不可观测就不可调试。必须看清 Agent 的思维过程，才能快速定位问题根源

### 问题六：经验难复用

- **后果**：资深员工精心设计对话生成完美数据分析报告，员工离开导致经验流失
- **原因**：知识和交互技巧存在于个人脑中，没有结构化沉淀
- **解法：引入 Skills（技能）机制进行团队级资产沉淀**——Skill 的定义（如何定义好的 Skill：具体可验证、避免矛盾）、Skill 粒度设计（太大不够通用、太小导致数量爆炸）、团队资产升级（从个人经验沉淀升级为组织复用资产）、Skill 安全管控（如何防止恶意指令或 Skill 投毒）
- AI 生产力必须从个人写提示词的技巧，升级为组织可复用的标准化资产

### 问题七：协作规模失控

- **后果**：多个 Agent 协同开发软件项目失败，任务冲突、结果相互覆盖
- **原因**：上下文污染与职责边界模糊，每个 Agent 都试图掌握全局
- **解法：分工明确，严格摘要回传**——职责边界隔离（严格区分主 Agent 与子 Agent，禁止越权操作；只有主 Agent 负责与用户交互 + 任务的规划和拆解）、严格摘要回传（子 Agent 仅回传结构化摘要，绝不允许倾灌全文）、异步协作（定义标准的通讯协议）、子 Agent 并发执行
- 必须确保主 Agent 的上下文始终保持纯净，始终聚焦于全局计划的推进

### 问题八：知识不沉淀

- **后果**：每次启动新项目，Agent 像个新人，都要重复纠正之前项目中犯过的错误
- **原因**：记忆架构缺失——LLM 每次推理都是全新的，缺乏长期记忆架构
- **解法：构建分层与带宽感知的企业级记忆架构**——顶层稳定知识（始终加载：构建命令、数据口径等企业稳定规范）、中层主题文件（按需读取：根据任务类型动态加载相关决策）、底层海量记录（仅检索不加载：历史记录按需检索，不占上下文）、静默知识蒸馏（后台整合：静默将对话经验蒸馏为持久项目知识）
- 没有记忆沉淀就没有复利，必须让 AI 记住纠错和规范，成为团队成长的成员

### 实施路线与框架：先建小闭环，再做平台化

1. **找准切入点**：高频、风险可控、验收明确，避免一上来就挑战核心业务核心系统
2. **定义边界**：写清交付物格式、质量及格线与不可越过的安全风险边界
3. **受控执行**：接入最少必要工具；建立工具登记册，在沙箱演练，设置高危操作的人工审批门禁
4. **闭环验证**：建立评测基线；沉淀成功与失败样例，设置发布门禁，让输出结果有客观证据支撑
5. **能力复用**：将跑通的上下文、工具组合与治理策略封装为可复用的 Skill

> Harness 落地挑战：新能力和旧体系的矛盾（例如：旧有系统的改造成本、团队习惯改变的阻力）。先在单个场景完成从意图到执行的工程闭环，验证后再做平台化，避免在不成熟的基座上堆叠复杂度。

## 实践原则：AI 时代的研发方式

Harness 不仅是技术框架，它也在倒逼团队工作方式的改变。

### 认知转变与 Label 范式重构

- **交互范式演进**：传统开发（人 → 代码，人是直接编写者）→ AI 协同阶段（人 ↔ 模型，人是审阅者）→ Vibe Coding 时代（人 → 文档 → 模型 → 代码，人是意图的表达者）
- **Label 范式根本转变**：
  - 补全 / NES 时代：用户手动修改 AI 生成内容——本质是人机协同纠错（AI 辅助，人兜底）
  - Agent 时代：人只提需求，代码无人工修改痕迹——本质是意图与执行的分层分工
- **最高质量的数据不再是"被修改的代码"，而是"被澄清的意图与验收标准"**

### 验证粒度跃迁与测试前置

- **从 Code Review 到 Function Review**：AI 一秒钟生成 500 行代码，人类花 10 分钟逐行 Review——未能提效，反而增加认知负担。关注点转移：放弃"代码实现细节"，转向"功能黑盒行为"的验证
- **测试前置：评测数据必须独立于功能开发**（共享上下文 = 考生自己出卷自己答题）：
  - 错误做法 ✕：开发完成后再补测试；同一模型会话生成功能与评测数据；测试通过即认为功能正确
  - 正确做法 ✓：需求阶段同步设计测试用例；评测数据独立于功能开发上下文；评测标准开发前锁定，不随实现变化
- 不要 Review 每一行代码，用独立测试用例约束行为——好的评测体系是质量的护城河

### Vibe Coding 的反噬与文档即契约

- **初期越快，后期越可能失控**：蜜月期开发极快、AI 独立完成大量功能；深水区面对大量"非自己编写"的代码，排查几乎不可能，甚至不如从头开始——隐形技术债的爆发
- **文档即契约：让大模型维护文档**：上下文来源（模型依赖文档理解项目现状）、团队契约（文档记录"为什么这样做"的决策逻辑）、同步流程（代码改动 → 触发更新 → 模型基于模板更新 → 人工 Review）、格式稳定（Skill 模板保障文档格式一致）
- 没有 Harness 约束的 Vibe Coding，是在透支未来的可维护性

### Harness 下沉为 AgentOS

> Harness 下沉为 AgentOS，是 AI 提效的迫切需求：让人彻底从工具操作中解放，只专注于目标表达。

- **上层：AI 原生应用层（人类唯一的工作界面）**——人只需表达目标与意图，不再关心工具调用、代码实现与执行细节，彻底解放人力
- **中间层：AgentOS（Harness 下沉后的智能体操作系统）**——自动承接意图解析、任务拆解、Agent 协作调度、上下文记忆与工具安全控制；现在 Vibe Coding 需要人工干预的所有环节，未来由 AgentOS 自动完成
- **下层：传统操作系统与底层算力硬件**——Windows / macOS / Linux、文件系统、CPU / GPU 计算资源
- 工作模式的跃迁：从 Vibe Coding（人写文档 → 模型写代码）到 AgentOS（人表达目标 → 智能体全自动交付），人类从执行者彻底升级为决策者
