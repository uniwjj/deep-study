# Data Agent vs Ontology Agent 推理对比

## 一句话结论

Data Agent 和 Ontology Agent 虽然共享同一个 Agent 循环外壳（感知→规划→工具→反思），但推理内核完全不同：Data Agent 在**维度树+指标字典**的封闭空间里做下钻归因，Ontology Agent 在**图结构+公理**的开放空间里做多跳推导。一个擅长解释数字变化，一个擅长揭示事物关联。

## 共享外壳

两者都遵循同一个宏观 Agent 循环：

- 接收自然语言目标
- 拆解为子任务
- 调用工具获取信息（SQL/OLAP API vs SPARQL/图数据库查询）
- 整合信息形成回答
- 必要时反思与纠错

都依赖 LLM 做规划和语言理解，都有记忆机制缓存中间结果，都能在出错时自我修正。但一旦进入"推理"环节，分岔就开始了。

## Data Agent 推理：归因与下钻

### 推理空间

**封闭但精确**的指标语义空间。每个指标自带"身份证"：计算公式、统计口径、可下钻维度（时间、地域、品类、渠道）、数据源、刷新频率。

### 典型推理链路（以"Q3 毛利率为什么下降"为例）

1. **确认异常**：拉取 Q3 和 Q2 毛利率快照，确认下降幅度（硬数字，SQL 可复算）
2. **维度下钻**：沿指标语义绑定的维度树逐层切开，每一步都是确定性的集合运算（GROUP BY），但 Agent 的"智能"体现在知道下一步切哪个维度、遵循帕累托原则
3. **交叉验证**：拉取关联指标（促销费用率、客单价、折扣率）寻找解释线索
4. **输出归因**："Q3 毛利率下降 3.1pp，主因是华北家电线下渠道促销折让扩大，贡献 -1.8pp"

### 推理本质

归纳与归因——在已定义的指标空间里做维度遍历和贡献度分配。每一步可复算（换 Agent 跑，口径一致则结果必然一致）。

- **强项**：精确、快速、可审计，擅长"掉了多少、掉在哪、谁贡献最大"
- **天花板**：指标语义里没定义的维度钻不下去——如果"竞品动向"没被做成指标，永远不会知道竞争对手也在降价

## Ontology Agent 推理：跳转与约束

### 推理空间

**开放但稀疏**的图结构。构成实体（供应商、零件、项目、法规）、关系（供应、依赖、合规、风险传导）、公理（如"若 A 是 B 的子公司，则 A 涉诉会影响 B 的授信额度"）。知道很多"谁和谁有关"，但不天然知道"关联的程度是多少"。

### 典型推理链路（以"供应商 X 能否按时交付零件 Y"为例）

1. **定位实体与意图解析**：在图中定位"供应商 X"和"零件 Y"，确认用户问的是交付风险
2. **多跳关系遍历**：不"下钻维度"，而是"往外跳"——从上游矿场跳到自然灾害事件、跳到物流商受灾状态、跳到其他客户的产能争夺
3. **公理与规则约束**：若本体定义了"上游原材料产地发生自然灾害则交付风险上调一级"，Agent 自动激活规则——这是确定性的符号推理
4. **不确定部分交 LLM**："暴雨停工三天"的影响程度由 LLM 读文本判断，封装在规则框架内
5. **风险传导汇总**：多跳路径上各段风险概率收口，给出最终结论

### 推理本质

演绎、关联与链接预测——在图结构上走路径，用规则做硬约束，用 LLM 做软判断。

- **强项**：开放域关联，能从供应商跳到矿场、天气、物流、竞争对手——回答"A 和 B 有没有隐藏关系"、"风险会怎么传导"
- **天花板**：本体覆盖率决定上限——图上没有的关系跳不出去，且多跳越长幻觉和噪声累积越严重，五跳以上若无公理剪枝容易变成"万物皆有关联"

## 对比总表

| 维度 | 指标驱动的 Data Agent | 本体驱动的 AI Agent |
|------|----------------------|---------------------|
| 推理原料 | 指标 + 维度 + 事实表 | 实体 + 关系 + 公理 + 挂载文本 |
| 典型推理动作 | 下钻 / 归因 / 同环比 | 多跳遍历 / 规则推导 / 链接预测 |
| 确定性来源 | 指标口径 + SQL 语义 | 本体公理 + 图查询 |
| 不确定性来源 | 维度选择策略、关联猜测 | LLM 对挂载文本的判断、多跳噪声 |
| 可解释性形态 | "华北贡献 -2.1pp，家电贡献 -1.8pp" | "X→Z→W，Z 停工三天，故风险中低" |
| 擅长回答 | "为什么跌？哪掉的？掉多少？" | "A 和 B 有没有隐藏关联？风险怎么传？" |
| 失败模式 | 口径不一致导致归因全歪 | 本体缺失或多跳幻觉导致结论虚浮 |
| 治理依赖 | 高度依赖指标语义治理 | 高度依赖本体完备性与规则质量 |

## 融合方案：同一推理链路上的交替上场

两者不应二选一，也不应并列运行、最后拼报告（那是并联，不是融合）。真正的融合是**在同一个推理链路上交替上场**：

1. **Data Agent 感知异常**：下钻定位到维度树叶子节点（如"华北家电线下 -1.8pp"），但解释不了了——因为"为什么"的原因（竞品动作、供应链扰动、政策变化）都不是指标
2. **结构化消息抛给 Ontology Agent**：带上指标名、下钻路径、异常幅度、未解释比例
3. **Ontology Agent 以锚点向外多跳**：发现铜价上涨、促销强度过高、竞品针对性补贴三条关联路径，回传
4. **Data Agent 做量化回捞**：铜价传导贡献 -0.9pp，促销折让贡献 -1.8pp，份额流失贡献 -0.4pp
5. **合并输出分层归因**：根因（本体侧）+ 量化（指标侧）+ 建议

> 地图指路，仪表读数。推理才算完整。

## 融合方案的工程化落地：8 层语义栈

上述融合方案在 [[data-agent-semantic-stack]]（Data Agent 8 层语义栈，2026-08 摄取）中得到了完整的技术化拆解——8 层中的四层恰好对应融合链路的四个环节：

- **指标层（Data Agent 侧）**：指标身份证（公式/聚合规则/维度树/过滤器）+ SemQL 接口，是下钻定位与量化回捞的执行底座
- **本体层（Ontology Agent 侧）**：实体/关系/公理 + SPARQL + MCP，是"以锚点向外多跳"的关系地图
- **事件层 + 锚定层（外部因素闭环）**：锚定层把铜价上涨、竞品补贴等非结构化外部事件挂载到本体实体，事件层以时序因果图谱（时间延迟/因果强度/因果类型）支撑"外部因素对毛利率的影响有多大"的因果追问

即：8 层语义栈把"交替上场"的推理融合范式落地为逐层可独立建设、可治理的工程架构。
