# 小米 Data Agent

> 核心主张：BIRD 榜单排名差异不在模型，在语义层的 Harness。Claude Opus 4.6 / GPT-5.5 裸打榜 30-90 名开外，加 Harness（腾讯、小米）冲进前五——Data Agent 决胜关键是 **NL2Semantic2SQL** 语义增强体系。只有模型不够，**可靠性来自 Harness 工程闭环，而非纯 LLM**。

本文合并两个来源：2026-06 公开报道（[[xiaomi-dimi-data-agent|原始文章]] 视角：BIRD 榜单与五大瓶颈）与 2026-08-11 DataFun 论坛演讲（方彪《从 BIRD 第三到生产可用：小米 Data Agent 落地实践》：系统全貌、五类不确定性及其解法闭环、实践案例）。

## BIRD 榜单：Text2SQL 领域"奥林匹克"

**BIRD**（Big Bench for Large-scale Database Grounded Text-to-SQL Evaluation）是目前 Text2SQL 领域公认最难、最权威的评测基准。

| 维度 | BIRD 特点 |
|------|----------|
| 数据库数量 | 95 个真实数据库 |
| 覆盖领域 | 37 个垂直领域 |
| 数据质量 | 含脏数据、缺失值 |
| 外部知识 | 需要业务知识（evidence）辅助回答 |
| 评判标准 | EX（执行正确率），答案对才算；VES 评估执行性能 |

核心原则：**SQL 写法不重要，执行结果必须和标准答案一致**。摒弃语句格式约束，评测规则与企业落地场景高度对齐。

2026 年，OpenAI、Claude、腾讯、快手等主流厂商积极参与打榜：

| 参赛方 | 方式 | 排名 |
|------|------|------|

| 腾讯 Data Agent | Model + Harness | 全球第五 |

最顶级基座模型裸打榜只排在 30-90 名，排名差异不在模型，在语义层 Harness。这与 [[code-agent-vs-data-agent|Code Agent vs Data Agent]] 的论调一致：企业数据分析需要系统设计补足模型能力缺口。

## 系统全貌：周活 5 万 BI 平台之上的分析 Agent

小米 Data Agent 是构建于周活 5 万的 BI 平台之上的**增强层**——BI 是基础，Agent 解锁 BI 未能覆盖的长尾诉求。BI 有"四堵墙"：专业要求高（要会搭看板、写 SQL）、不够智能（只展示数值不分析）、灵活性差（新增指标排期数周）、决策不闭环（看板看完就结束）。分析 Agent 对应解锁：自然语言对话、智能根因分析（异常自动诊断+维度拆解）、即问即答灵活下钻、规则+行动闭环（接入业务规则与 Action，从分析直达决策）。

### 五层架构

```
用户层    数据生产消费一站式 SKILL（集成-开发-治理-问数-分析-可视化-报告）

Agent层   营销Agent（圈选|投放|洞察|归因）· 分析Agent（问数|根因|报告|可视化）
          · 开发Agent（定义即开发|调度|运维）· 治理Agent（资产|权限|血缘）
          分析能力：意图路由（Router）· 上下文（Context）· 任务规划（Planner）
          · 分析Skills（数据问答/指标问答/模型问答/文档问答 + 异常检测/根因分析/
          时序预测/维度拆解/归因分析/智能洞察）· 评测优化（评测用例自构建/效果自迭代）
语义层    语义增强（指标|维度|关系）· 历史查询 · 知识文档 · 冲突检测
          指标 | 维度 | 关系 | 知识 | 描述 | 业务流程
基础设施  模型部署（LLM / 私有LLM / Mify服务 / 指标BI / 知识库SKILLS / Matrix | Milvus /
          sandbox）· 质量监控 | 版本迭代 | 评测回归 | 安全沙箱 | 权限

```

### 分析 Agent 两条链路

- **消费态**（用户视角，对话即分析）：①对话式问数（自然语言、多轮追问、SKILLS 调用）→ ②智能分析（异常检测、根因分析、诊断建议）→ ③可信呈现（报告审查、数据溯源、HTML 可视化）
- **配置态**（管理员视角）：①数据与语义接入（数据导入、语义管理、知识配置）→ ②Agent 调优闭环（Agent 配置、评测模块、效果自迭代）→ ③上线与监控（行列权限、线上监控、渠道接入）

### 落地现状

集团内部：**10+ 业务领域规模化落地、千级周活用户、数千份分析报告与数据洞察、10x+ 用数·分析·决策提效**。外部：BIRD 全球第三。"权威榜单问的是能不能解题，生产环境问的是能不能长期稳定地答对。"

## 生产级 Data Agent 的五类不确定性

从「能解题」到「长期稳定答对」，是一条贯穿 输入 → 生成 → 度量 → 迭代 → 运维 的真实卡点链：

| # | 环节 | 不确定性 | 具体表现 |
|---|------|---------|---------|
| ① | 输入 | 数据质量差 | 命名混乱、口径不一致、字段缺注释 |
| ② | 生成 | 生成不稳定 | 同一问题多答、复杂 SQL 易错、数字不可信 → 模型幻觉 |
| ③ | 度量 | 评测集难建 | 冷启动无 Query-SQL、人工标注慢、覆盖不足 → 好坏无从衡量 |
| ④ | 迭代 | 优化成本高 | 评测→分析→补语义→再评测、链路长耗时 → 优化跟不上 |
| ⑤ | 运维 | 上线后衰减 | 数据/表结构变化、业务口径变化、无人维护 → 准确率持续降 |

## 解法体系

### ① 数据质量：多级语义回退架构（Metric → DSL → Reject）

四级回退，每级置信度递减，"宁可不说，不可错说·保护业务决策底线"：

| 级别 | 路径 | 信任度 | 说明 |
|------|------|--------|------|
| 1. 指标层 Metric | Text2JSON | ★★★★★ 极高 | 官方认证指标库（原子/衍生/复合指标，业务域/口径/标签/认证）；有指标直接查，高可信路径 |
| 2. 语义模型层 | Text2DSL + 内置解析 | ★★★★☆ 较高 | 度量（SUM/COUNT/AVG、字段校验·歧义检测）、维度（地区/时间/类目）、关系（JOIN 路径·笛卡尔积拦截，1:1/1:N/M:N）、实体（primary/foreign/unique）；聚合粒度·GROUP BY、行列权限；业务可自由建设，SQL 经过解析后执行 |
| 3. 底表层 | 湖仓·直查数据库（LLM 直生成 SQL） | ★★★☆☆ 中等 | ODS/DWD/DWS/ADS；无语义约束，需人工校验 |
| 4. 兜底 Reject | 明确拒答 | — | 不输出任何数据；引导优化（建议换问法·推荐指标）、反馈闭环（驱动模型建设）、用户教育（标注能力边界）；无可信来源即拒答 |

配套**质量打分 + 血缘/日志驱动的增强建议**：语义增强 Agent（表特征分析：schema、数据粒度、表描述、业务知识、使用场景；字段特征分析：邮箱类/Id 类、时间类型 yyyy-mm、枚举值有限、空值率高）+ 诊断建议 Agent（枚举值标注、时间特征、空值类型标注、歧义检测、禁用推荐），结合生产作业、代码、查询历史、数据血缘计算质量分（表描述质量分、字段丰富质量分、字段歧义分），质量分 **>80 分才开启问答**；用户操作（采纳/拒绝/修改/自定义）人工审核；同时抽取指标口径（BI 组件、查询逻辑、指标定义、去重）。

### ② 生成稳定：多路生成投票

四阶段流水线 + 两阶段选择，将评测集回测波动率从 **±5% 降到 ±1%**：

- **Stage 1 · DBU**：AI 诊断增强——供给判别模型、维度值字典、长/短分析、业务文档、黑话知识、选表/关联
- **Stage 2 · NLU**：改写、分词、多路召回排序、Schema Link、Verified Sql、骨架 Few-shot
- **Stage 3 · NLG**：多模型生成（Mimo、dc、dc_md 等）
- **Stage 4 · 置信度感知两阶段选择**：执行聚类投票（候选按执行结果 **MD5 分组**，confidence = 最大簇/总数）；confidence ≥ 0.6 → 高置信度捷径（取最大簇首个 SQL）；否则 Pairwise 判别模型（score = conf × win，top-2 簇比较、argmax 选最终 SQL，3 次自洽多数票）
- **SQL Fixer**：同一 LLM 修复，fix_retry=3，执行报错/空结果立即修复
- **多路耗时保障**：异步并发、超时丢弃、Prompt cache（cache key & 固定前置）
- **Stage 3.1 · Greedy 最优组合搜索（离线）**：候选池 N LLM × M 策略 = T generator，在 dev 集上逐个回放各 generator 准确率，贪心逐步加入、聚类投票重评、选边际提升最大、top_k=T 停止，锁定最优组合 best_combination；Pairwise 判别模型离线对抗训练（Coder 基座、对抗难例、判别头 SFT、生成负样本对、A/B 选择）

### ③ 生成可信：可解释即可信任（数据溯源）

五步溯源链，保证每个数字可回查：

1. **Data Agent 生成报告**（多步推理 Agent：规划·取数·分析·成文）
2. **数字捕获 & 来源分类**：优先埋点 claim 读取（生成时数字打 claim_id、占位符携带工具上下文）；对缺 claim 的文本数字回抽；兼底：规则/大模型抽取
3. **来源绑定（工具/推理）**：每个可溯源数字 → 产生它的查询（SQL/根因/python）；多候选冲突 → 降级
4. **置信度标注**：工具调用[置信度 高]、大模型计算[中]、大模型推导[中]；LLM 推导类标 untraceable，直送降级
5. **可信报告交付**：数字+SQL、可下钻数字（每个数字可点击 → 来源）；综合置信度分级 高/中/低/不可溯源，低级醒目标警；解析计算链（聚合/过滤/JOIN/衍生公式拆解）、标记不可溯源

### ④ 评测构建：冷启动三大来源

- **方式一：基于 BI 看板生成——看板的数据即标准答案**：看板分析 Agent 抽取看板知识（分析全局筛选器如"用户默认查询昨天数据""默认只看正式员工"、分析组件筛选如"活跃=最近7天pv>10"），获取组件 DSL/描述器，用户选择语义模型，描述器转 DSL(SQL)、SQL 执行、数据一致校验、人工审核落库，产出 QA 对+知识（如"应届生指应届生界别不为空"）
- **方式二：基于表字段智能生成**：多选配置（自由选择指标、维度、时间；风格参考：趋势查询、对比查询），批量生成直接产出评测集样本（按配置一次性生成 100 条 Query-SQL 样本，要求问题自然流畅不生硬）
- **方式三：基于用户行为智能挖掘——越问越准**：用户行为信号分层（点赞=强·正、点踩/报错=强·负、多轮/空/其它=弱·待定 → AI 补判）；AI 预标注只打草稿（SQL 草稿准确率有限仅作起点）；人工审核·可信闸门（AI 草稿只是参考，人来确认/修改/拒绝，审过的才算数）；落库两个产出：**评测集**（正样本=query+可信SQL，负样本=query+修正SQL）+ **知识副产品**（表/字段描述·业务口径，反哺语义层增强）。诊断错因：选表/口径/语法/缺知识。**"一个动作确认三样：对错·SQL·知识"——用户每一次反馈都在喂养系统，越用越准**

### ⑤ 优化提效：Loop 评测-归因-增强闭环

用户只需确认评测集，主动/定期一键迭代，系统自动评测、错误分析、语义沉淀、再评测：

1. **全量评测**（text2sql + Judge）
2. **错误分类 Agent**：识别失败样本，归为 N 类——选表错误 / SQL 语法 / SQL 逻辑 / 语义理解 / 结果偏差
3. **按决策表路由修复策略**（人工优化经验沉淀）：SQL 语法→校正语法；选表错误→选表知识；SQL 逻辑→改写查询；语义理解→补充知识；结果偏差→校准口径
4. **审查 Agent** 逐条审查沉淀经验（是否具备泛化性？是否与已有知识矛盾？修改是否引入新错误？口径/定义是否清晰可复用？）——通过/打回
5. **应用修改**：保存版本快照 v(N)/完整产物链、修改语义层文件
6. **重新评测** → 退出判断：达标停止 / 暴露瓶颈 / 退化则自动回退；未达标继续下一轮

用户一键开启优化、优化完成飞书通知、优化后用户审核。

### ⑥ 抗衰减：回测监控 + 增量沉淀 + 语义层 CI

"90% 上线只是起点"——数据/表结构/口径持续变化，无人维护 → 准确率逐日下降。三道防线：

| 防线 | 机制 | 价值 |
|------|------|------|
| 01 评测集持续回测 | 定期自动回测，效果下降自动告警 | 及时发现：量化衰减、定位方向 |
| 02 线上 query 增量沉淀 | 不浪费每次真实提问，持续归集为增量评测集养料 | 自动补充：反哺迭代 |
| 03 语义层变更 CI | 像代码变更一样走审批，变更前后自动对比评测效果 | 变更审核 |

## 五大生产级瓶颈

### 瓶颈一：查数幻觉——模型不认识你的业务世界

大模型训练数据里没有企业的业务规则和字段命名，导致系统性失败：

**缺失背景知识**
- "小米集团有多少人？" → 模型不知道表存的是在职数据，用通用知识瞎猜
- "ITP 这个部门今年的预算有多少？" → 模型不知道 ITP = 基础技术平台部，直接 `WHERE department = 'ITP'`，查不到结果

**缺失业务规则**
- "上周的漏损订单量是多少？" → 严格规则：用放款完成日期筛时间、交付日期 IS NOT NULL、当前机构是否自营 = 0。规则只在业务文档里，模型每次猜的不一样

**枚举值陷阱（隐蔽杀手）**

| 场景 | 字段实际存储 | 模型猜测 | 结果 |
|------|------------|---------|------|
| 查三星员工 | `Samsung` | `三星` 或 `三星集团` | 0 条，静默失败 |
| 查已完成订单 | `status = 1`（1=完成，0=开始，2=异常） | `status = 'completed'` | 报错或空结果 |
| 查手机品类 | `PHONE` 和 `phone` 混存 | `'phone'` | 漏掉一半数据 |

> 这不是模型不够聪明，是业务知识无法靠训练学到。

### 瓶颈二：深度分析不是代价高，就是完全错误

"有了 LLM + Text2SQL 就能做根因分析"是 Data Agent 领域最常见的误区。

**加法类指标：能做，但代价极高**
- "导致 12 月净收入波动的四级团队有哪些？"
- 无专用工具：模型拆成 N 个 SQL → 查 12 月 → 查 11 月 → 逐行心算差值 → 排序。调用次数从 1 次骤增到 N 次，响应时间 3 倍+，累积错误率急剧上升
- 有根因分析工具：1 次调用，底层引擎完成全部计算

**除法类指标：完全无法正确完成**
- "导致 12 月利润率（利润/收入）波动的四级团队有哪些，贡献度是多少？"
- ⚠ 实测：针对除法逻辑指标，大模型**完全无法完成任务**，且会输出看起来合理实则严重错误的答案
- 模型做法：分别查各团队自身利润率变化 → 用减法算差值 → 把"自身变化幅度最大"的团队认定为主因
- 这是根本性逻辑错误：极小规模团队利润率从 -97% 变到 +129%，对整体贡献微乎其微。**"自身变化幅度"和"对整体的贡献度"是两个不同概念**
- 正确答案需要替代法/杜邦分解算法——大模型靠 Text2SQL 凑不出来

**海量维度下钻：上下文溢出**
- "分析 11 月整体毛利率下降，具体下钻到哪些 SKU 导致的（10 万+ SKU）"
- 10 万行数据不可能全塞给大模型，模型强加 `LIMIT 50`——分析冰山一角，遗漏长尾根因

### 瓶颈三：表越多，关联越乱

真实业务场景：几百张表，字段命名各异，无物理外键，无 ER 图，关系在 DBA 脑子里。

| 问题类型 | 示例 | 后果 |
|---------|------|------|
| 选表错误 | 两张表都与"离职"相关，只有 data owner 知道哪张准确 | 基于错表做分析 |
| 关联错误 | A 表 `user_id` = `ID_123`，B 表 `user_id` = `123`（无前缀），直接 JOIN | 0 条数据，无报错，静默失败 |
| 数据膨胀 | 一对多关系未去重 | 指标数值翻倍，营销预算基于错误数据做决策 |

这类问题靠优化提示词无法根治，需要**结构化的关系模型**约束 SQL 生成边界。

### 瓶颈四：效果不稳，全靠人盯，成本高

SQL 执行成功 ≠ 答案正确。语义是否正确依赖业务知识，只有人能判断：

| 问题 | 现实 |
|------|------|
| 线上准确率怎么量化？ | 只能人工标注，成本大，无法规模化 |
| 模型升级后会不会退化？ | 无自动回归测试，只能人工逐一验证 |
| 发现 badcase 怎么修？ | 依赖研发手工调优 Prompt，迭代极慢 |

> 没有评测-回归-迭代的闭环，上了生产就是玄学驱动开发——今天跑通的 query，明天换个措辞可能就失败，没有人知道为什么。

### 瓶颈五：权限是合规红线

[[claude-code|Claude Code]] 和 Codex 的定位是个人效率工具。企业数据分析面对：

- **表级隔离**：普通员工不能查高管专属财务表
- **行级隔离**：A 部门员工不能看 B 部门薪资数据——同一张表，每行可见范围不同
- **Prompt 注入防护**：恶意用户通过构造特殊 query 绕过权限限制

这些需求靠提示词无法可靠保证，需要系统级权限管控，且要通过合规验证。企业数据安全不能建立在"大模型理解了权限要求"这个假设上。

## NL2Semantic2SQL：语义层是 Harness 核心

业界共识路径是 **NL2Semantic2SQL**，包括 OpenAI、Snowflake 等官方博文在讨论 Data Agent 时，重点都是语义层建设。

语义层的核心价值：
- 将业务知识（字段含义、枚举映射、数据质量规则、表关系）结构化为可被 Agent 调用的知识资产
- 在 NL→SQL 过程中注入业务上下文，消除幻觉
- 提供结构化关系模型约束 SQL 生成边界

这与 [[ontological-semantic-layer|本体化语义层]] 和 [[dataagent-semantic-layer|DataAgent 语义层]] 的理念一致，但 Xiaomi DiMi 的实践更强调语义层在 **Harness 工程化**中的位置——语义层不是静态知识库，而是可评测、可回归、可自进化的基础设施。

## 实践案例：数量级跃迁

### Before vs After

| 场景 | 之前 | 之后 | 量级 |
|------|------|------|------|
| 快速问数 | 1h–1天 | **17 秒** | 数百倍 |
| 根因分析 | 1–3 天 | 2–5 分钟 | 天→分 |
| 分析报告 | 1 周 | 10 分钟 | 周→分 |
| 新业务接入 | 月+ | 天+ | 月→天 |

效率提升的核心不是「快」，是把人从「重复取数中解放出来」。

### 案例一：金融场景（天星数科）——问答 + 问数双需求

- 业务需求：一线人员多、海量文档+数据，同一人两类需求并存；**90%+ 准确率（金融级精度）、20x+ 效率提升（小时→分钟）、800+ 评测集**（持续运营验证）
- 解法：意图识别自动分流——**问答走 RAG（文档问答：多轮澄清意图）、问数走 SQL（Verified SQL：多路投票、数字溯源），支持 RAG+SQL 复合**；"问数+问文档，一站式满足一线全部数据需求"

### 案例二：人力资源场景——分析维度 + 可视化报告

- 业务需求：分析多样（应届生/中管/蓝领/白领，同一批 HR 数据）、报告多样（可视化模板差异、报告精简差异）
- 数据：**200+ 月活用户、3.2 次周人均对话（消费频次）、首次自主取数（非技术零门槛）、覆盖多部门 HR**
- 解法：Skills 沉淀分析思路（多轮澄清）+ Skills 沉淀可视化模板（HTML 报告风格：深度/精简/月度）；"分析思路统一，报告模板可复用，非技术 HR 也能拿到专业级输出"

### 案例三：账单分析场景——可溯源 + 结果到人

- 业务需求：生成报告（提出洞察）→ 跟进验收（找到负责人、量化验证效果）→ 落实整改（异常根因诊断）→ 签字确认 → 数字到人、行动闭环、状态持续追踪
- 数据：**3天 → 10分钟、10+ 领域覆盖**
- 解法：数字溯源（数不可信·异常说不清）→ 生成→保存→签字→推送→跟进闭环；"DataAgent 负责洞察，人 Review 报告内容——从数字可信到优化落地"

## 新业务接入 SOP：中台 × 业务，标准化接入

整体接入周期 **1-2 周**，四步走：

| 步骤 | 周期 | 内容 |
|------|------|------|
| 1. 数据接入 | 2-3 天 | 部署交付（AI 数据增强：诊断补全、智能字段补全）；数据范围·口径 |
| 2. 评测构建 | 2-3 天 | 评测集构建（AI+看板自动·小时级）；指标口径·业务知识；验证 QA·人工审核 |
| 3. 效果优化 | 2-3 天 | Loop 自进化（错误归因·自动迭代）；问答与确认 |
| 4. 上线迭代 | 持续进行 | 线上回测监控、核心指标监控；业务赋能（分析思路·领域专家参与） |

**Delta + Echo 共建**：Delta（中台平台侧 FDE）+ Echo（业务领域侧 FDE）——一名懂数据的业务 FDE + 中台平台能力，1-2 周跑通新业务接入。

## 经验与展望

### 分析 Agent 需要 Harness

数据分析不是写代码——**没有护栏、答案唯一、无法确定性验证**（SQL 执行成功不代表正确）。只有模型不够，可靠性来自 Harness 工程闭环：评测/回测/监控/迭代的完整工程，而非纯 LLM。

### AI 时代分析 Agent 门槛很低

三重红利叠加，各团队都能快速自建垂域分析 Agent：
- **基建红利**：元数据获取（表结构/字段/血缘）、数据查询（标准查询接口已开放）、CLI 开放、零启动成本（无需自建基础设施）
- **场景红利**：范围有限（聚焦该垂域数据与指标）、业务理解深（垂域团队最懂自己数据）、免口径对齐（无需跨域语义治理）
- **成本红利**：AI 工具（Claude/Codex）降门槛、Skills 机制复用分析流程与知识、Agent 调用快速嵌入现有 Agent

### 门槛这么低，中台重点做什么？

门槛很低，人人都能做。**但，做得起 ≠ 做得久**。三个新痛点对应中台三个重点：

| 痛点 | 中台重点 |
|------|---------|
| 01 语义维护成本越来越高（数据与口径持续变化，自建治理设施不划算） | 语义层治理基础设施：标准化语义层结构、业务语义一键高效导入、配套 CI/版本/血缘影响分析 |
| 02 线上准确性如何持续保障（保障持续答对需专门工程，重复造轮子不划算） | Harness 持续进化：评测/回测/监控成本更低，业务接入成本更低 |
| 03 数据前链路缺完整方案（完整链路需多 Agent 协同，单团队建不全） | 全链路整合方案：打通开发·治理·分析三类 Agent，开放 CLI/Skills——不要求必用，但更好用 |

> **中台不做别人做不了的事，而做别人做起来不划算的事。**

### 未来演进：评测闭环 + 自进化框架

Data + AI 的终局核心在两点：
1. **低成本的"评测-回归-迭代"闭环**
2. **自进化的、越用越懂业务的 Agent 框架**

全球第三是阶段性验证，Data + AI 真正的价值是以此为基础对业务流程的重构与变革。
