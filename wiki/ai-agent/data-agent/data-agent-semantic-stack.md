# Data Agent 8 层语义栈

## 核心主张

**Data Agent 的聪明不在模型参数里，而在它脚下踩着的语义世界里。** 模型是发动机，语义栈是路——它告诉 Data Agent：这个世界有什么东西、它们怎么关联、指标怎么算、规则是什么、哪些能做哪些不能做、错了怎么改。

作者明确声明：8 层语义栈是**观点框架，不是行业标准**，价值在于启发不在照抄；实际落地时应映射到现代数据栈已有成熟组件（指标层、语义层、知识图谱、RAG 锚定、Agent 编排框架、治理总线）。分层本身是对的——软件工程基本原则：每一层只关心一件事，接口清晰，治理横切。

## 8 层全景

| 层次 | 回答的问题 | 核心方案 |
|------|-----------|---------|
| 第一层 指标语义层 | 业务指标是什么、怎么算、口径有没有变过 | Metrics Layer / Semantic Layer（dbt MetricFlow、Cube、LookML） |
| 第二层 本体语义层 | 世界上有什么东西、怎么关联 | 知识图谱 Schema（OWL/SKOS）+ 实体解析 |
| 第三层 过程/事件语义层 | 事情怎么发生、先后顺序、因果链条 | 时序因果图谱 + 事件溯源 |
| 第四层 锚定语义层 | 非结构化信息怎么挂到结构化世界 | AEVS 框架 + MetaRAG |
| 第五层 意图/任务语义层 | 用户想要什么、Agent 该做什么 | Agent 规划器 + 任务模板库 |
| 第六层 规则/约束语义层 | 哪些能做、哪些不能做 | Policy Engine + 规则库 |
| 第七层 能力/权限语义层 | 谁可以做什么、能用什么工具 | RBAC/ABAC + MCP 工具注册中心 |
| 第八层 会话/反馈语义层 | 怎么记住上下文、从错误中学习 | Agent Memory + 反馈闭环 |

横切暗线：**治理总线**——事件驱动架构 + 治理引擎 + 工单闭环 + 仪表盘。

## 第一层：指标语义层

地基，也是技术最成熟的一层。没有它，Data Agent 不知道"毛利率"是哪个口径、今年和去年口径是否同一套。

- **存储**：dbt Semantic Layer（MetricFlow）、Cube、LookML 或自研指标定义引擎；指标定义写成版本化代码（YAML/MQL）纳入 Git 管理
- **指标身份证**：公式（如 `Net Revenue = SUM(payments) - SUM(refunds)`）、聚合规则（SUM/COUNT/AVG/COUNT_DISTINCT）、维度树（时间/地域/品类/渠道/客户群）、过滤器（排除测试订单、剔除退款）、口径版本 + breaks 列表（记录每次口径变更的时间点与影响范围）
- **接口**：Data Agent 不直接生成 SQL，而是生成 **SemQL**（语义查询语言），由语义层翻译成 SQL——**Text2Semantic2SQL** 模式。直接生成 SQL 要自己处理表关联、聚合语法、方言差异，表结构一变 SQL 就废；走语义层 Agent 只关心"要什么指标、什么维度、什么时间范围"
- **一致性校验**：取数前校验对比周期的口径版本一致性；跨越 breaks 点自动触发口径对齐或显式标注"口径有变化"
- **加速**：多级缓存、自适应 CTE 提取合并 IO、谓词下推、自动化物化视图

一句话总结：指标层是 Data Agent 的"度量衡"，没有统一度量衡，数字就没有可信度。

## 第二层：本体语义层

指标层回答"毛利率是多少"，本体层回答"毛利率和华北区、冰箱品类、线下渠道是什么关系"——它是关系地图。

- **建模语言**：OWL（W3C 标准，表达力最强，适合复杂业务）或 SKOS（更轻量，适合快速起步）
- **存储**：图数据库首选——Neo4j（属性图，工程生态最成熟）、Amazon Neptune（RDF + SPARQL）、腾讯云图数据库；超大规模可考虑 Apache Jena + S3
- **核心设计**：实体（如 `region_north_china`、`category_appliances`）、关系（如 `supplies`、`sold_via`）、公理（约束规则，如"客户消费满 20 次即视为优选客户"）
- **接口**：SPARQL 端点 + MCP Server——Agent 通过标准协议访问图数据，不关心底层是 Neo4j 还是 Neptune
- **与指标层映射**：每个维度成员挂载本体 URI（"华北"→`region_north_china`）。Agent 查到"华北区毛利率下降"，可一跳找到华北区所有门店、供应商、竞争品牌做归因分析
- **构建路径（反共识架构）**：不需要物理集中所有数据——通过协议适配接入 ERP、MES、CRM 等异构系统，逻辑层做语义对齐，对外提供标准化数据服务 API，既降成本又保留各系统自治性

## 第三层：过程/事件语义层

最难、最容易被忽视的一层。指标层说"毛利率降了 5 个百分点"，本体层说"毛利率属于利润指标"，但都没回答"**为什么**"——事件层回答这个为什么。

- **事件建模**：事件溯源（Event Sourcing）模式，业务事件不可变追加写入，JSON Schema 定义结构
- **存储三层**：实时事件流 Apache Kafka + Kafka Streams（毫秒级摄入）；事件存储 Apache Cassandra 或 ScyllaDB（高吞吐时序写入）；因果图谱图数据库（与本体层共用或独立部署）
- **时序因果图谱**：节点是事件，边是因果关系；边附带属性——时间延迟（cause 发生后多久 effect 出现）、因果强度（0-1）、因果类型（直接/间接/共因）
- **因果发现算法**：PC 算法（条件独立性检验，适合变量少）、NOTEARS（神经网络，适合高维）、Granger 因果（时序预测，适合金融/销售等时序密集场景）
- **状态机建模**：SCXML 或 BPMN 2.0 定义流程状态迁移（如促销活动：策划→审批→上线→运行→复盘→归档），每个状态转换都是一个可被因果图谱捕获的事件
- **接口**：`event_query(event_type, entity, time_window, causal_depth)` 返回事件子图与因果路径——可问"Q3 毛利率下降，前三个月发生了什么事件？按因果强度排序"
- **与锚定层联动**：外部事件（铜价上涨、竞品补贴、政策变化）通过锚定层挂载到实体，再流入事件层形成因果链，才能回答"外部因素对毛利率的影响有多大"

## 第四层：锚定语义层

结构化世界与非结构化世界的桥梁——行业报告、新闻资讯、内部纪要、竞品分析、政策文件如何融入 Agent 推理链。

- **AEVS 框架**（Anchor-constrained Extraction with Verifiable Provenance）：三阶段、带字符级出处追踪的 LLM 知识图谱抽取框架
  - 阶段一 锚点发现：微调 LLM 对文本做 token 级重要性打分，筛选高置信度实体/事件/关系片段；启用上下文锚点标记（`[[EntityName]]` 格式）建立文本锚点↔本体实体双向链接
  - 阶段二 受约束抽取：基于预定义关系 Schema 抽取 (主体, 关系, 客体) 三元组，每个元素必须 grounding 到显式文本证据（字符级出处）。四级匹配策略区分"忠实抽取"与"幻觉"：精确匹配→直接入库；模糊匹配→打标待审；Schema 匹配→标注"推断"；文本搜索匹配→标注"低置信度"
  - 阶段三 覆盖感知补充：监控锚点利用率，对未使用锚点触发额外抽取轮次；sentence embeddings 语义去重防跨轮次冗余三元组
- **存储与出处**：三元组入图数据库与本体层融合，每个三元组带 provenance 元数据：`source_doc_id`、`chunk_location`、`confidence`、`timestamp`、`extraction_round`
- **置信度传递**：Agent 引用锚定信息时置信度带入推理链——高（>0.9）结论笃定；中（0.7-0.9）标注"据有限信息推测"；低（<0.7）标注"需人工核实"
- **工程选型**：抽取用 LLM（GPT-5/Claude/DeepSeek）+ 结构化输出校验；向量检索 Milvus 或 Pinecone；图存储 Neo4j
- **编排策略**：FlattenedRAG + StructuredRAG 混合。FlattenedRAG 枚举元数据组合、把结构化元数据转化为非结构化问答知识库，准确度高；StructuredRAG 利用元数据结构特性、先召回核心指标再过滤维度，解决长尾问题

## 第五层：意图/任务语义层

Data Agent 的"大脑皮层"——前四层定义世界是什么样的，这一层定义用户想要什么、Agent 该做什么。

- **意图本体（Intent Ontology）**：定义所有可能的用户意图类别——指标归因、趋势查询、异常诊断、风险预估、What-if 模拟；每类意图挂载常用槽位（slot）：指标名、时间窗、维度、对比基准、输出格式
- **槽位提取**：LLM + 结构化输出（JSON Schema 强制约束），不允许自由发挥
- **任务模板库**（核心资产）：每种意图一个标准拆解模板
  - 归因类：确认异常 → 维度下钻 → 卡点识别 → 外部因素排查 → 量化回捞 → 归并输出
  - 趋势类：确定指标 → 选定时间范围 → 趋势拟合 → 拐点识别 → 周期性分析 → 输出
  - 诊断类：确认症状 → 假设生成 → 数据验证 → 排除法 → 根因定位 → 输出
- **规划器**：Agentic Harness，如 LangGraph、AutoGen、CrewAI——负责任务路由、多 Agent 协作、规划循环、上下文工程
- **接口协议**：调用指标层用 SemQL，本体层用 SPARQL，事件层用 event_query，锚定层用 MetaRAG
- **存储**：意图本体 JSON Schema；任务模板 YAML 或 Python DSL，版本化 Git 管理

## 第六层：规则/约束语义层

Data Agent 的"护栏"。没有规则它可能违反合规、触犯数据隐私红线、在错误场景给出错误建议。

- **三类规则**：合规规则（数据敏感度分级、GDPR/SOX、数据出境限制）；运营规则（指标阈值告警如毛利率低于 30% 触发、异常交易拦截）；建议规则（战略客户豁免、不可一刀切、需人工复核场景）
- **引擎选型**：OPA（Open Policy Agent，Rego 语言，生态成熟性能好，适合云原生）；Drools（Java 生态，适合已有 Java 技术栈）；自研轻量规则 DSL（灵活性最高，维护成本最高）
- **校验时机**：Data Agent 输出结论之前——生成答案前最后一道安检
- **规则冲突检测**：每日自动扫描规则库检测冲突并报警（如"毛利率低于 30% 报警"与"战略客户豁免所有报警"冲突，需人工裁决）
- **变更治理**：规则变更走治理闭环——提交变更申请 → 审批 → 测试 → 灰度发布 → 全量上线，每一步有记录

## 第七层：能力/权限语义层

谁可以做什么、Data Agent 能用什么工具。财务分析岗能看到利润表但看不到员工薪资，运营岗能看到日活但不能看财务数据。

- **RBAC + ABAC 混合**：RBAC 粗粒度——每个角色一个可见域（财务分析岗看所有财务指标，运营岗只看运营指标）；ABAC 细粒度——结合环境属性：时间（工作时间之外不能访问敏感数据）、地点（只能公司内网）、数据敏感度（高敏感需双重认证）
- **MCP 工具注册中心**：Agent 的能力清单，每个工具定义：名称、输入参数、输出格式、调用权限、调用频率限制、计费规则
- **执行原则**：Data Agent 只能调用它有权限的工具；权限决策运行时实时执行，不走缓存
- **审计**：权限变更必须审计——每次授予/撤销/修改有记录、时间戳、审批人

## 第八层：会话/反馈语义层

Data Agent 的"记忆皮层"。没有它 Agent 永远是新手——每次对话从零开始、同样的错误反复犯。

- **Agent Memory 三层**：短期记忆（当前会话上下文——消息历史、已确定指标版本、已走 Hop 路径；Redis 存储，TTL 24 小时，会话结束即释放）；长期记忆（跨会话用户偏好、常见纠偏记录、高频问题模板；PostgreSQL 或 MongoDB，带用户 ID 和时间戳，保留 90 天）；全局记忆（平台级错误模式库、最佳实践库，定期从反馈提炼，永久保留）
- **三类反馈**：显式（点赞/点踩、评分、纠偏意见）；隐式（是否复制答案、继续追问修正、导出/分享——行为比语言更诚实）；系统（Agent 自检到的低置信度、对账失败、超时重试，自动上报）
- **反馈闭环流水线**（精髓）：① 反馈事件结构化记录（类型、会话 ID、Agent 输出快照、用户操作）→ ② 每日批处理聚类同类错误（LLM + Embedding 聚类，text-embedding-3-small + KMeans）→ ③ 根因分析（是哪一层出的问题：指标定义/本体路径/锚定信息/规则配置）→ ④ 生成改进工单（分配给对应层 owner）→ ⑤ 人工审核后更新配置或代码 → ⑥ 部署上线 → ⑦ 效果追踪（错误还在出现吗？修复率多少？）
- **工程选型**：短期记忆 Redis Streams + TTL；长期记忆 PostgreSQL + pgvector（语义检索历史会话）；反馈流水线 Apache Airflow 调度每日批处理；错误聚类 LLM + Embedding

## 横切暗线：治理总线

8 层没有治理就是一盘散沙。治理不是单独一层，是横切所有层的暗线。

- **治理事件来源（每层各自的事件）**：指标层（口径变更、版本断裂、一致性校验失败）；本体层（实体新增/废弃、关系变更、歧义检测）；事件层（因果链路断裂、状态机异常）；锚定层（置信度下降、来源过期）；规则层（规则冲突、命中率异常）；权限层（越权尝试、权限扩散）；会话层（高频纠偏、重复错误）
- **统一事件 Schema**：事件类型、发生层、时间戳、上下文快照、严重级别、建议 action
- **治理工作流**：事件 → 事件总线（Kafka/RabbitMQ）→ 治理引擎（判定是否需人工介入）→ 自动修复（缓存刷新、规则热更新）→ 人工工单（口径变更审批等）→ 修复闭环 → 效果追踪
- **治理仪表盘**：各层健康度评分（示例：指标层 95%、本体层 88%、锚定层 72%）、高频错误 TOP10 及趋势、治理 backlog 及平均修复时长、Data Agent 回答准确率趋势（基于反馈数据）
- **工程选型**：事件总线 Kafka；治理引擎自研轻量引擎 + OPA 规则校验；工单 Jira 或飞书多维表格；仪表盘 Grafana + Prometheus

## 架构全景与落地优先级

**全景**（表层→中层→底层 + 横切）：
- 表层（Agent 直接消费）：意图层（Agent 规划器 + 任务模板库）、规则层（Policy Engine + 规则库）、权限层（RBAC/ABAC + MCP 工具注册中心）、会话层（Agent Memory + 反馈闭环）
- 中层（世界理解）：指标层（Metrics Layer）、本体层（知识图谱 + OWL）、事件层（时序因果图谱 + 事件溯源）
- 底层（桥梁）：锚定层（AEVS + MetaRAG）
- 横切：治理总线

**三阶段落地**（8 层全建不现实）：
1. 第一阶段（3-6 个月）：指标层 + 意图层 + 会话层 + 治理总线雏形——跑通"归因类"核心场景并采集反馈，最小可行产品
2. 第二阶段（6-12 个月）：本体层 + 锚定层 + 规则层——提升"世界理解"能力与安全性，核心竞争力
3. 第三阶段（12-18 个月）：事件层 + 权限层完善——解决最复杂的时序因果与权限治理，差异化优势

**结论**：8 层语义栈不是一个产品，是架构思想。每一层都有成熟技术方案可复用（dbt/Cube、Neo4j/OWL、Kafka/Cassandra、RAG/知识图谱抽取、OPA、RBAC/ABAC、Redis/PostgreSQL、Kafka/Grafana），不需要从零发明，只需要组装好、对接好、治理好。
