# 腾讯 Data Agent 设计实战

> 场合：DataFun「AGENTIC AI 超级智能体系统架构峰会」· 2026-08
> 本 PDF 包含两段演讲：冯浩哲《Data Agent 生态 我们的上半年》（13 页）+ 王柳焮《Data Agent 设计实战：知识准备、库表检索与 SQL-Python 混合计算》（24 页）

## 一、冯浩哲：Data Agent 生态 我们的上半年

**演讲者**：冯浩哲 · 腾讯 TEG 大数据智能体算法负责人（WeData · 腾讯云 BI · 全民 BI · AMS Adata）

### 被质疑（2026.01 – 2026.03）

以 Claude Code 为代表的 CLI harness 爆火，「干掉中台」成为最有感染力的图景——人手一个 Agent CLI，目标干掉 SaaS、去掉中台；中台只需开放 Skills / MCP，本地接上 Agent 就开干。团队双线作战：把 Skills / MCP 做好适配各家 CLI harness；同时重新回答"我们为什么有必要存在"。

为此对 Claude Code（约 57 万行 TypeScript）做了逐模块深度拆解，结论：**三个技术原因 + 一个场外原因**：

| # | 原因 | 内容 |
|---|------|------|
| 一 | **代码是文本，数据不是** | 代码是纯文本，grep/glob/read 直接进上下文，毫秒级本地磁盘 I/O，错了再搜反复渐进；数据是结构化记录，一个分区动辄 10GB，放不进上下文只能靠 SQL 间接访问，分钟级集群计算资源，必须一次找准。"Claude Code 没做任何代码索引——纯文本搜索快到成本可以忽略。但你没法对一张几亿行的表做 grep。" |
| 二 | **代码随时有正反馈，数据没有** | 代码反馈回路闭合：写代码 → 编译/运行 → 报错=明确反馈 → 模型自我修正 → 在 1M 上下文里反复试错；数据反馈回路断开：写 SQL → 平稳运行零报错 → 条件不对/join 写错/选错字段/理解错口径 → 南辕北辙的数字，唯一反馈是用户自发纠正或默默不再使用。"数据场景最阴险的地方：失败是静默的。没有任何正反馈能让模型做对。" |
| 三 | **缺乏中心化维护的 Skills 一定会腐化** | Anthropic 官方博客实测：精心维护的 Skills 下准确率 95%，用户增加、维护减少，一个月后跌至 65%（95% → 65%）。次要原因：Code Agent 指令空间被占满——9 个代码工具 + system prompt ≈ 1 万 token，模型能严格遵循指令的有效窗口业界经验仅 ~16K；Skills listing 预算仅上下文 1%、每条描述限 250 字符；MCP 工具全部延迟加载 → 在 Coding Agent 里 data 永远是二等公民 |
| 场外 | **安全** | 数据接入外部 CLI 后，审计链路中断——推着团队做中心化 Data Agent |

### 怎么做：三个痛点，三件事（一一对应）

| 痛点 | 解法 |
|------|------|
| 数据不是文本 | → 统一库表知识体系 |
| 数据没有正反馈 | → SQL + Python 混合计算 |
| Skills 会腐化 | → LLM as a Judge 知识运营 |

**事一 · 统一库表知识体系**（对标 Unity Catalog，解决「检索不动」）：

- 三个知识维度：以「数」为中心（广义元数据——存储/运维/安全，库表字段描述、tag）；以「业务」为中心（指标/维度/特征）；以「平台」为中心（用户手册/历史工单/平台建设文档）
- 规模挑战：日活跃库表千万级、字段上亿，comment 大面积空白——纯人工梳理走不通
- AI 增强知识系统闭环：每天清洗两类 SQL（生产 SQL（同步/计算任务）+ 用户 SQL）→ AI 反推（表怎么来的 · 谁在用 · 算什么口径）→ 用户确认/补充（人机闭环的关键位）→ 沉淀为平台 Skills（反哺知识体系）
- 量化效果：**找表召回率 41% → 79%**（视频号业务数百条真实 Query 实测，已逼近人工精标上界）

**事二 · SQL + Python 混合计算**（解决「没有正反馈」）：

- 业界主流 SQL 端到端派：Databricks + Metric View，语义层收口径；SQL 按死在 ETL 取数下推数仓，只许选分区/选字段/选条件/基础聚合（min·max·sum·avg·count·distinct）/仅 left join
- 腾讯的现实：数据源横跨 hive / PG / StarRocks / MySQL，没有统一方言与引擎，复杂 SQL 生成准确率大幅下跌
- 方案：大数据过滤聚合在数仓完成（TB 级也算得动）→ 小结果集出 → 分布式 Python 接手分析（百 GB 级内存计算——特征工程/建模/可视化）；中间结果、报错直接回给模型自我修正
- 量化效果：**腾讯云 BI 真实业务问题集准确率 56% → 90%**

**事三 · LLM as a Judge 评测系统**（解决「Skills 会腐化」）：

- 每晚 LLM 自动评测：对当天每一条用户 tracing 打分，分流两类 case：满意/纠错后完成任务 → 萃取用户知识 → 写成 Skills → 反哺知识体系（用户每一次纠错 = 平台一次进化）；明确负面情绪（「不是这样」「你懂不懂啊」「继续继续」）→ 收进 badcase 池 → 挨个研究怎么解

### 路线 vs 行业（2026.6 Data + AI Summit 给出的场外答案）

- **Databricks**：同样被问「要不要把平台能力 MCP / CLI 化」——答案：优先中心化平台。真正以「自研 Agent 调 MCP servers」为主流用法的只有极少数具备成熟自研能力的头部客户，绝大多数客户不具备去中心化运营能力（客户使用模式分布示意：MCP 模式·极少数 / 平台模式·绝大多数）。DBX 的判断：「平台一旦被工具化，可替代性就大幅提升」。押注 Genie One + Genie Ontology 自动知识图谱——准确率大幅跃升，显著优于标准 RAG
- **Snowflake · Horizon Context**：「没有上下文，在猜；有上下文，agent 才干活」
- **Anthropic · 内部实践**：准确率 21% → 95%
- **OpenAI · 内部实践**：复杂问题回答 22 分钟 → 1 分 22 秒
- 诚实的观察：Databricks 也不轻松——真正把 Genie One 用好的客户仍是少数，单客户交付动辄以月计、重度依赖专家驻场。方向共识已形成，坑大家都在填。**这是我们的机会窗口。**
- 结论：决定 Data Agent 上限的，是中心化维护的上下文知识层

## 二、王柳焮：知识准备、库表检索与 SQL-Python 混合计算

**演讲者**：王柳焮 · 腾讯 TEG 大数据 Data Agent 负责人

### 数据链路的 Agentic 重构

「上个月各业务线流水对比情况如何？」——用户只问了一句话，背后是四个环节依次衔接：1 库表查询（找哪张表、哪些字段能回答这个问题）→ 2 代码生成（用 SQL / Python 写出计算逻辑）→ 3 数据计算（在引擎上执行，处理规模与安全）→ 4 结果生成（解释结果，形成可读结论）。Data Agent 设计实战的本质就是对这条数据链路的重构。

### 聚焦典型业务痛点

| 痛点 | 表现 |
|------|------|
| 01 找表难 | 元数据缺失严重：表和字段语义大量空白，**元数据缺失率约 85%**；人工治理不可持续：头部业务动辄上千张表、每表数百字段 |
| 02 口径乱 | 业务语义存在多重歧义："上个月流水"同时牵动组织、指标与时间三类定义；SQL 语法之外还需识别企业内部指标定义与业务语义 |
| 03 算不动 | 本地计算存在内存瓶颈：pandas 面对大规模数据容易撞上内存墙，TB 级任务常需工程师改写 PySpark；数据下载到本地拉长分析周期，增加安全与合规成本 |

### 三条主线解法

- **知识准备**：解决"Agent 看不懂数据"——将无语义、分散的数据资产沉淀为可理解、可检索、可更新的业务知识
- **库表检索**：解决"Agent 找不到正确数据"——运行时按需定位正确的表、字段和口径，逐步消解业务歧义
- **SQL-Python 混合计算**：解决"Agent 面对大数据算不动"——在可信环境中结合 SQL 下推、Python 沙箱与分布式异构计算完成分析闭环

### 知识准备

**统一语义层 / AGENT 标准数据语料库**：01 指标标准化（定义、粒度与计算逻辑保持一致）；02 AI 可信查询（业务词典、系统过滤与 Golden Queries）；03 多源数据虚拟化与整合（跨引擎形成统一的数据视图）；04 自主决策（Agent 在治理规则下执行操作，形成从洞察到行动的闭环）。

面临的问题：元数据治理难（治理需数月；表和字段标注为空比例约 85%；数据孤岛；头部业务动辄上千张表每表数百字段，人工标注消耗大量人力）；多种计算口径（交付周期周级；跨引擎方言——同一查询在 SR / PG / Spark / MySQL / SuperSQL 等引擎间存在语法差异；复杂代码门槛高；口径歧义——"上个月流水"同时牵动组织、指标、时间三类定义）。

**关键举措**：用 AI 将生产 SQL、查询行为、Schema、数据分布和血缘逻辑，沉淀为 Agent 可消费的数据语料库：

- **自动元数据增强**：输入生产 SQL（真实业务查询与计算逻辑）、查询流水（表与字段的使用行为）、原始 Schema（结构、类型与命名信息）、库级业务背景（业务域、主题与场景解释）；LLM 逆向推导表语义——从真实数据使用信号中还原表在业务链路中的位置与价值（这张表从哪里来 / 被谁使用 / 解决什么业务问题）
- **字段级 Profiling 增强**：为何需要——字段名和 comment 经常不足以表达业务含义，数据分布能揭示字段是维度、指标、时间或实体 ID；手段——取值分布、直方图、最大/最小/均值、枚举 Top-N、码值字典、字段角色；自动识别字段角色，判断字段能否支撑问题，减少语义缺失带来的召回偏差

**直接收益**（439 Query 测试集）：

- 视频号找库表准确率：业务精标人工上界 **81.17%** / 无元数据基线 **41.02%** / 自动增强元数据本方案 **79.49%**
- 腾讯云 BI 协同问数准确率：未 Profiling 基线 **56%** / 加入 Profiling 本方案 **90%**

### 库表检索

从人工检索（经验驱动：翻 Wiki、问同事、试写 SQL；同题可能走向不同候选表，检索路径缺少稳定过程，结果难以复用与审计；人工反复验证业务口径）到 Agent 检索（运行时按需调用）：从业务问题定位候选表（先用轻量级知识缩小范围，避免全量 schema 进入上下文）→ 用字段与数据分布验证可用性（确认指标、维度和过滤条件是否由候选表支撑）→ 按需追溯血缘与计算逻辑（将"相似表"收敛为可解释、可执行的正确口径）。

**渐进式披露检索 L1-L4 分层知识体系**（将数据知识从轻到重拆开，让 Agent 只获取当前判断所需的最小信息）：

| 层级 | 内容 | 回答的问题 |
|------|------|-----------|
| L1 表级元数据 | 表名/中文名、摘要/业务主题、数据粒度 | 哪些表可能相关？快速定位候选业务表 |
| L2 字段元数据 | 字段名/数据类型、字段描述/角色、主键与关联字段 | 字段能否支撑问题？校验指标与维度承载能力 |
| L3 字段 Profiling | 取值分布/枚举 Top-N、码值字典、最大/最小/均值 | 字段语义是否可信？用真实数据补齐字段语义 |
| L4 血缘与计算逻辑 | 上下游关系/字段血缘、派生公式/指标逻辑、Join Path | 口径是否可以追溯？解决复杂口径与跨表关系 |

轻量信息快速缩小范围 → 按需下钻随信息需求逐层加载 → 复杂知识精确对齐口径。

**落地成果**（Spider 2.0 · 547 case）：

| 指标 | L1 表级 | L2 字段 | L3 Profiling | L4 血缘 |
|------|--------|--------|-------------|--------|
| 检索闭合率 | 11.9%（L1 闭合） | 30.5%（累计） | 78.6%（累计） | 100%（L4 闭合） |
| 累计召回率 | 0.680 | 0.880 | 0.940 | 0.967 |
| 累计精确率 | 0.130 | 0.510 | 0.600 | 0.680 |

- L3 独立贡献 48.1%，字段真实取值与码值信息是闭合率提升的关键
- 表召回率提升至 96.7%，复杂问题可继续借助血缘和计算逻辑判断口径
- 精确率由 0.13 提升至 0.68，分层语义信息持续降低候选噪声

### SQL-Python 混合计算

**通用 Agent 架构**（数据规模通常小于 10GB）：原架构执行边界——数据分析在本地单机环境完成：Agent 提问 → SQL 全量数据提取（数据出域，存在风险）→ 数据清洗 → 生成 Python 代码 → 原生 Pandas 单机引擎 → 结果。局限：本地单机能力有限（pandas 易受内存墙约束，单机、单并发、CPU 算子限制明显）；数据安全风险高（全量数据下载到本地，增加出域、合规与安全风险）。

**DataAgent 架构**（数据规模可达 TB 级，计算在可信的分布式环境中完成）：

- SQL 下推到分布式引擎（过滤、聚合、Join、采样下推到数仓或分布式引擎，避免全量数据拉到本地）→ 分布式采样 → 数据特征提取 → 生成 Python 代码 → cuDF 数据清洗 + 数据分析（GPU 加速）→ 结果
- SQL 负责大规模计算；Python 负责灵活分析（轻量结果进入可信环境，继续完成特征工程、统计分析、可视化与结果解释）

**Agent 动态选型**（运行时信号：数据规模（分区、预估返回集）、计算类型（关系计算/灵活分析）、安全边界（数据是否留在可信环境）、执行反馈（样本、计划与异常状态））：

- D1 生成 SQL 的时机：01 跨源数据 → SuperSQL 统一取数（✓ 统一数据文件格式）；02 试探取数（✓ 试执行；✓ 快速获取表数据缺失信息）
- D2 执行 SQL 的程度：01 结果集可被多次分析（✓ 免来回 SQL 取数）；02 取数范围可算极限值（✓ 避免后链路分析失败）
- FEEDBACK LOOP：模型判断可能偏离边界，需要不停校正——样本不符、计划异常或规模超限时，回到试跑与路由环节，调整 SQL 改写或执行面选择

**直接收益**（原生 pandas vs cuDF（单机））：

| 数据维度 | pandas read 耗时 | pandas 计算耗时 | cuDF read 耗时 | cuDF 计算耗时 |
|---------|-----------------|----------------|---------------|--------------|
| 600M | 2.04 s | 2.91 s | 0.08 s | 1.19 s |
| 3G | 7.91 s | 12.77 s | 0.14 s | 1.82 s |
| 10G | 24.43 s | 40.43 s | 0.79 s | 4.27 s |
| 30G | 72.31 s | 177.77 s | 4.35 s | 11.64 s |

三句话收益：**数据不出云**（大数据计算在云端或可信环境完成，降低数据下载和本地处理带来的安全风险）；**算法不撞墙**（避免 pandas 本地内存瓶颈，支持更大规模数据分析任务，充分发挥分布式异构算力）；**工程不排队**（减少分析师等待工程师改写 PySpark 的成本，由 Agent 自动完成 SQL 与 Python 之间的执行分工）。

### 总结与未来规划

总结：**懂数据**（AI 元数据增强、字段 Profiling、血缘和计算逻辑，让数据资产具备可理解的业务语义）；**找得准**（L1–L4 渐进式披露和自规划工具调用，按需定位正确表、字段和口径）；**算得动**（SQL 下推、Python 加速沙箱，让可信环境中的大规模分析可持续执行）。

未来规划两条主线：知识侧 01 广义统一元仓（统一上下文入口，知识从单次 → 资产，覆盖从找表 → 全量；知识源覆盖：文档类 iWiki、代码类知识源、Skill；知识资产化飞轮：搜表、资源、授权、任务）；评测侧 02 常态化评测系统（评测从周期性 → 常态化，评估从单点 → 全链路；持续沉淀评测基准（GT）；联合评估：Agent 轨迹、工具调用、成本）。
