# 需求语义翻译

企业微信团队在 [[mailplugin-feature-dev-skill|邮件插件 Skill]] 中沉淀的一套规则化体系，把"产品语言 → 代码语言"这道翻译工程化、可执行化，让 AI 也能独立完成。

## 问题：翻译链的五类翻车点

产品同学说的"加个红点"和工程师写的 `setMailboxBadgeValue:` 之间有一道语义鸿沟：

| 翻车点 | 真实场景 | 代价 |
|--------|---------|------|
| ① 范围错判 | PRD 段落整体讲"后台配置"，中间"手机上看到的效果"被当口语忽略 | 漏实现移动端 UI |
| ② 归宿不明 | 设计稿 9 张移动端候选，AI 只挑 2 张，其余笼统当"参考图" | 漏 7 个独立页面 |
| ③ 联想扩大 | 用户说"点 A 拦截"，AI 联想"按一致性 B 也应该拦" | 改了不该改的逻辑 |
| ④ 关键词找不到 | 直接 grep "小红条" → 0 命中；只 grep "tips" → 800+ 处淹没 | 定位失败或误命中 |
| ⑤ 找错文件 | "邮件红点"翻译错位置，改了 RMail 而不是 MList | 功能完全走错地方 |

## 五个确定性规则

### ① 范围识别：硬关键词表

用 **强信号关键词表** 硬触发，不依赖 LLM 语义理解：

| 类别 | 关键词（命中即强制打"移动端"标签） |
|------|----------------------------------|
| 平台/端 | 手机上、手机端、移动端、iOS、Android、客户端、App |
| 原生控件/交互 | Toast、弹窗、浮层、小红条、红点、Tab角标、下拉刷新、侧滑、长按 |
| iOS 系统组件 | 状态栏、导航栏、Home Indicator、底部安全区、刘海 |
| 移动端页面术语 | 输入法、键盘展开、全屏弹窗、actionsheet |

**硬规则**：即使段落主旨在讲后端/配置/推送规则，只要任一关键词命中，那一段描述的功能点就必须单独拆成移动端项。

### ② 设计稿归宿：每张图必须归类

候选清单里每张设计稿都必须归宿明确，归到三类之一：
- 对应某个需求点
- 筛选误纳（从候选清单移除）
- 需求点遗漏（新增需求项）

**禁止用"参考图"当万能垃圾桶**。某张图归不到任何需求点时，要么是筛选误纳、要么是需求点遗漏——不允许存在"未归类"。

### ③ 拦截点清单：禁止语义联想

任何"点击 X → 触发 Y"类拦截，X 必须有具体引用依据。**依据只接受三种**：
- 设计稿标注（PNG 上的连接线/箭头，须有 nodeId）
- 文档原文（TAPD/企微文档的直接引用原句）
- 用户消息（用户原话引用）

禁止凭业务语义作依据（"Z 看起来也属于这类""为了一致性""属于同类功能行为"等一律删除）。填不出具体引用的行直接删掉，不实施。

### ④ 五维搜索矩阵

把产品语言扩展成代码搜索词。一个需求点从 5 个维度交叉扩展：

| 维度 | 出发点 | 命中什么 |
|------|--------|---------|
| ① iOS 事件方法 | 平台标准 API | `didSelectRowAtIndexPath:` / `handleTapGesture:` / `touchUpInside:` |
| ② 功能语义 | 产品意图的英文同义词 | "小红条" → tips / banner / warning / notice / alert |
| ③ OC 命名习惯 | 项目里的命名前缀 | `show*` / `handle*` / `on*` / `goto*` / `setup*` |
| ④ 协议/代理 | 谁通知谁 | `tableViewDelegate` / `<XxxDelegate>` / `didSelectXxx:` |
| ⑤ 通知/回调 | 跨模块通信 | `XxxNotification` / `XxxCallback` / `XxxHandler` / `RACSignal` |

**设计哲学**：五个维度不是按"和需求最相关"排，是按"代码里实际可能出现的位置"排。① 是平台层、② 是业务层、③ 是项目命名风格层、④⑤ 是跨模块通信层——任何一个 UI 行为必然落在这 5 层之一。

联想的依据来自 [[code-knowledge-base-pyramid|三级代码知识库]]：L2 模块 wiki 提供文件级语义，Glossary 提供命名约定。有这两份知识的联想命中率 > 80%，没有则是"瞎猜"。

#### 联想 vs 拦截的边界

- **⑤ 联想**（搜索用）：找代码改哪里时，必须用领域知识扩展候选搜索词，只是缩小搜索范围，不直接影响实现
- **③ 拦截**（决策用）：决定 X 触发 Y 是哪条交互时，必须有具体引用依据，直接决定实现内容

一句话：**联想用于搜索，引用用于决策**。

### ⑤ 结构化产出：五列表 + `subtasks.json`

拆解阶段的产物同时包含人类可读和机器可读两份：

**五列表格**：

| 序号 | 需求项 | 类型 | 数据来源 | 关联设计稿 nodeId |
|------|--------|------|---------|-------------------|
| M1 | 邮件列表顶部小红条 | 新增 UI | CGI 字段 `is_show_warning_icon_in_mailtab` | 153:74513 |
| M2 | Tab 角标显示感叹号 | 修改逻辑 | 已存字段 + 优先级判定 | 153:74600 |
| M3 | 点击小红条跳转管理页 | 新增交互 | TAPD 原文（已引用） | 153:74521 |

**`subtasks.json`**：

```json
[
  {
    "id": "M1", "title": "邮件列表顶部小红条", "type": "新增UI",
    "data_source": "CGI字段is_show_warning_icon_in_mailtab",
    "figma_node": "153:74513", "depends_on": []
  },
  {
    "id": "M2", "title": "Tab 角标显示感叹号", "type": "修改逻辑",
    "data_source": "已存字段", "figma_node": "153:74600", "depends_on": ["M1"]
  }
]
```

`subtasks.json` 承担三个角色：**接力台账**（跨会话状态传递）、**依赖图**（自动推导执行顺序）、**完成度追踪**（每完成一个子需求标记 done）。

## 红线机制

Skill 用 YAML + 分层加载的红线系统约束 AI 行为：

- **Critical（6 条）**：全流程必守，启动即加载，违反会直接造成线上事故或严重返工
- **Standard（30+ 条）**：按阶段加载，违反会污染工程规范

**触发即停 + 模板化报告**：

```
⛔ 触发红线 RL-XX：<标题>
当前情形：<具体说明>
建议处理：<回退到哪个步骤 / 需要用户确认什么>
```

### 代表性 Critical 红线

| 红线 | 来源 | 设计思想 |
|------|------|---------|
| RL-02 企微文档必须走 `wecom-cli` | `web_fetch` 只能拿到 HTML 外壳 | 每种来源专用通道 |
| RL-15 编译必须通过 | "AI 说做完了但编译都没过" | 退出码 0 = 唯一判据 |
| RL-16 未按阶段执行 | "用户一句话 → AI 跳过拆解直接改代码" | 后一阶段输入 = 前一阶段产出 |
| RL-17 禁止 LLM 手工分桶 | "AI 看图选稿"的随机性 | 脚本直方图 + LLM 只补判 UNCERTAIN |
| RL-21 禁止语义联想扩大 | "AI 自作主张越界" | 填不出引用的行直接删除 |
| RL-29/30 UI 改动规范 | "设计稿走样" | 禁止硬编码 + 视觉对齐逐项核对 |

### 落盘判定（Sentinel File Pattern）

任何长跑命令的成功证据都是"文件存在"，不依赖 stdout（terminal 会截断/置后台）：

```
# 编译成功的唯一判据：build_report.txt 存在
# commit 成功的唯一判据：git log -1 <hash> 更新
```

## 完整翻译闭环

```
需求侧（产品语言）          代码侧（工程语言）
  PRD 一段话    →           L1 overview.md 选模块
  设计稿 nodeId  →           L2 <module>.md 锁文件
  CGI 字段名     →           L3 figma_token_mapping.md 翻译 UI
  用户原话       →           Glossary 扩展搜索词 → grep → 读片段
```

两条链一对接，AI 就拥有了独立开发完整需求所需的**全部确定性输入**。真正的提效不在"AI 写代码"，而在"AI 不再需要人来当翻译"——开发者从"PRD 翻译机"升级为"AI 的产品经理"。
