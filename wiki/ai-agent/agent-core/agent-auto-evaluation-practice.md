# Agent 自动化评测实践

> 2026 Agent 大会「Agent评测与治理论坛」演讲：**寇宏达**（阿里巴巴淘天集团·1688-AI评测负责人；10+ 年数据科学，B2B、近场电商、金融风险，AI+数据工作流改造），主题《从"能跑"到"可信"——AI 评测驱动 AI Agent 自迭代，1688 Agent 自动化评测实践》。

> 贯穿全篇的主张：**评测系统自己，也需要被评测。**

## 评测边界：三种评测解决三类不同问题

| 维度 | 传统软件测试 | AI 基模评测 | AI 应用/Agent 评测 |
|------|------------|-----------|-------------------|
| 被测对象 | 代码与确定性逻辑 | 模型的通用能力 | 模型 + Prompt + 工具 + 数据 + 环境 + 交互 |
| 核心问题 | 功能是否正确、改动是否回归 | 能力、鲁棒性、对齐 | 真实任务能否稳定完成 |
| 常用方法 | 单测 / 集成测试 / Assert | Benchmark / Eval / 模型对比 | 自动化评测 + 人工复核 |
| 典型输出 | Pass/Fail、缺陷定位 | 能力分数、排名与能力边界 | 完成度、根因、准出与改进 |

四层能力：样本与分析（数据集/SOP）、评测工程（Trace 与 Outcome）、Judge 工程（Rubric/规则）、Agent 工程。

**Agent 评测评的不是一个模型，而是一套在真实任务中运行的系统。**

## 真实场景与问题定义

一条电商任务可能在 6 个地方"看起来成功"（理解 → 规划 → 工具 → 数据 → 决策 → 交付）——从用户意图到最终交付是一条长链而不是一次问答。真实坏例：用户要求寻找符合泰国标准的插座，召回含"通用孔/万能孔"的商品，用户连续多轮纠错仍未收敛；任务确实返回商品，但强属性约束、纠错收敛和最终交付同时失败。

问题定义：**Task × Trial × Trace × Outcome**（同一真实任务、重复运行、保留完整轨迹、核验真实环境结果）；混合判定（按问题选择判定方式）。从"一次答对"转向"多次稳定、过程可证、结果真实"。

## 数据集迭代：离线固定集 + 线上真实日志

不是二选一：**固定集回答"改动有没有退化"，线上日志回答"用户到底遇到了什么"。**

| | 离线固定测试集 | 线上真实日志 |
|---|--------------|------------|
| 优势 | 条件可控、版本可比；适合回归与准出；Badcase 可长期沉淀 | 用户真正高频的任务；系统无响应、额度、限流；多轮纠错与新增需求信号 |
| 盲区/挑战 | 输入太规整，覆盖不了真实分布；甚至可能出现泄题、矛盾和映射错位 | 日志缺失、版本混杂、无标准意图，需要先做意图识别、筛选和可评测化 |

### 首次线上真实日志分析（6 月抽样）

878 用户 Session、946 意图单元、288 有效抽样阅卷、整体均分 64.2，完全完成率仅 42.4%。未满分案例主要根因：Agent 无响应 38%、积分/额度异常 22.2%、交付关键内容缺失 22.2%、系统执行报错 9.5%。

**71.6% 的问题首先来自系统与基础设施；模型能力只是其中一层。**

## 全景架构：双轨评测

一条 SOP，四个技术关口。离线黄金集守住已知质量，线上真实日志发现未知问题，两类证据汇入同一改进闭环：

1. **标准可执行**：固定/动态 Rubric、黄金集持续更新
2. **证据可验证**：工具/多模态结果可核验、线上日志可回放
3. **Judge 可信**：结论强制锚定原始证据、报告自检驱动提准
4. **闭环不退化**：失败自动归因与路由、修复后自动回归、不退化才发布

流程：离线黄金测试集 + 线上真实日志 → Task/Trace/Outcome → Rubric/Verdict/根因标签 → 归因 → 修复 → 自动回归 → 准出门控；人工把关（标准确认、异常复核、发布决策）。

## 标准设计：双门槛准出

```
准出 = 执行完整率 ≥ 90% AND 端到端结果分 ≥ 80
```

- **门槛 1 执行完整率**：必经步骤是否完成？工具是否真的调用？任务是否中断或被兜底掩盖？
- **门槛 2 端到端结果分**：结果完整性 + 结果有效性——有没有给全？能不能直接用？数据、计算、逻辑是否可信？

双门槛避免"结果写得漂亮，但关键步骤根本没执行"的假通过。

## Rubric 工程：把业务语言改写成可执行契约

"结果合理"不是标准，机器无法执行模糊共识。差的写法（"推荐结果合理，报告完整。"）不知道检查哪些字段、不知道多严重算失败、无法从轨迹找到证据、同一 Judge 会自由发挥。可执行的契约：

| 要素 | 示例 |
|------|------|
| 检查项 | 推荐商品 ≥ 5 条且不重复 |
| 通过条件 | 国别标准属性必须命中 |
| 证据 | 引用轨迹原文 / 工具返回 / 交付字段 |
| 严重度 | 核心项 / 一般项 / 加分项 |
| 门控 | 强约束不满足 → 总分直接不通过 |

Rubric 的价值不是"描述更详细"，而是让判定可复现、可审计、可回归。

### 固定 Rubric：确定性长链任务

适合采购、跟单、补货、经营分析等有明确 SOP 的任务。六步检查单：解析意图（query 约束不丢失）→ 调起能力（工具选择与参数正确）→ 取回数据（返回成功且字段齐全）→ 计算分析（口径、公式、排序正确）→ 用户确认（写操作前必须确认）→ 结构化交付（表格/报告可直接用）。

同一条轨迹被三类检查同时复用：执行完整性（必经步骤/工具/状态）、输出完整性（字段/表格/章节）、内容有效性（事实/计算/逻辑/合规）。**固定 Rubric 的核心不是"固定答案"，而是固定必须发生的业务事实。**

### 动态 Rubric：开放式任务

一把固定尺子会把"具体需求"磨平。为每个输入生成实例级检查清单，再用统一规则聚合。示例（Query：夏日冲锋衣）：红线（类目不能偏离；关键信息不得编造）、重要（轻薄/透气/夏季适用证据充分；防风防泼水与目标场景匹配）、加分（给出清晰选购建议与取舍）。

**动态生成"评什么"；规则引擎仍决定"怎么算"。** 两类能力并行：确定性任务守住流程，开放式任务尊重实例差异。

## 多模态切片评测

多模态评测不能只看总分：整体 7/9（77.8%），位置识别仍然可以是 0。同一张肖像图整体准确率 77.8%（9 个问题答对 7 个），能力切片后位置关系识别为 0/1。切片维度：对象计数、场景主旨、对象属性、对象位置、对象识别/动作 QA。

一切片，盲区就暴露——位置关系没有被识别出来，却被总体准确率稀释了。

## Judge 可信度：Observation → Analysis → Conclusion

每个结论都能穿透到原始证据：

1. **观察**：引用轨迹原文 / 工具状态 / 交付字段
2. **分析**：解释为什么满足或违反这条 Rubric
3. **结论**：输出 Pass / Fail 与失败标签

示例：观察"工具返回的商品属性为'万能孔'，用户已明确要求'泰规'"→ 分析"强属性约束未命中，且用户连续纠错后仍未收敛"→ 结论"意图理解偏差 + 数据过滤缺失，门控失败"。

**LLM 负责"看懂证据"，规则引擎负责"计算分数"；模型不能同时当裁判和计分员。**

## 评测系统自检：Judge 的"偷懒"有固定模式

扫描 900 条 Verdict 记录（260 个文件、10,026 个判项的早期全量扫描）：

| 问题 | 占比 | 表现 |
|------|------|------|
| Fail 证据弱 | 56.7% | 短于 20 字符或缺轨迹锚点 |
| Pass 走过场 | 46.4% | 大量使用"前置未触发" |
| 同 Case 分差 ≥ 30 | 4.7% | 跨会话一致性不稳定 |
| 分数与扣分不一致 | 1.7% | LLM 还会算错加减法 |

根因不是"模型突然变笨"：单次 Prompt 判太多项 → 后半段注意力衰减；证据格式宽松 → seq=3 也能过；模型同时判定和算分 → 错误没有确定性兜底。**评测自动化的最大风险：把人工不一致，规模化成机器不一致。**

### 七道确定性闸门

防幻觉/防偷懒：把"纪律"写进运行时，而不是只写进 Prompt。

| 闸门 | 机制 |
|------|------|
| G1 证据强度 | 短证据自动重判 |
| G2 反证原则 | 无反证不允许 Fail |
| G3 模板化检测 | 理由雷同整条重判 |
| G4 过度跳过 | Pass 率异常触发复审 |
| G5 分数重算 | 规则引擎重新计分 |
| G6 方差裁决 | 跨会话差异触发仲裁 |
| G7 数值对账 | Python / 规则计算优先 |

输入侧：微批次 + 顺序随机化；输出侧：证据三段论 + 单项重试。**能用确定性规则解决的，绝不再问一次大模型。**

### 复审与收敛：让 Judge 不再"一次判定"

Worker 先判，Checker 复核；只对异常项有限重判（整批最多重判一次），把人审留给真正的分歧；定期巡检小样本人工仲裁。已落地：原文证据、分数重算、一致性审计；推进中：自动复审、有限重判、跨轮 Memory 与经验复用。

## 两类入口

| | 离线评测 | 线上日志评测 |
|---|---------|------------|
| 回答的问题 | 改动后有没有退化？现在能不能发？ | 真实用户正在遇到什么？ |
| 样本 | 版本化黄金集 + 历史 Badcase | 真实调用日志、异常链路与高频需求 |
| 方法 | 重复运行、版本对照、关键切片回归 | 分层采样、聚类归因、异常与新需求发现 |
| 产出 | 稳定性结论、退化定位与修复验证 | 未知问题、真实分布与 Badcase 素材 |

上线准出建立在离线评测之上（离线集上的整体 + 关键切片双门槛）；线上发现 → 脱敏与分层 → 回流离线黄金集 → 修复回归/准出 → 上线继续观测。**线上把真实问题带回来，离线把修复是否可信说清楚。** 两类入口共享 Task、Rubric、Judge、归因标签和报告契约。

## 准出案例：94.41 分为什么不准出

渠道热门商品查询 · 28 条评测记录：端到端结果分 94.41（≥80 通过）AND 执行完整率 89.29%（<90% 不通过）→ 最终判定不准出。**高分不能抵消关键步骤缺失。**

## 自动归因：从分数到根因

7,170 个 Session 自动归成 10 类问题（一轮全量评测：3,206 个问题 Session、12,354 条失败明细；44.7% Session 含失败项，每个问题 Session 平均 3.9 条失败明细）。Top 失败根因：系统执行异常 34.2%、产出完整性缺陷 14.3%、结果分析错误 12.8%、任务规划缺失 12.1%、工具调用错误 8.4%、交互策略不当 5.8%、数据获取缺陷 5%。

标签必须落到"失败明细"粒度而不是给整个 Session 贴一个大标签——同一条任务可以同时存在规划缺失、工具参数错误、交付字段缺失。这让报告从"谁分低"变成"应该修哪一层"。

## 驱动迭代：评测是"问题翻译器"

把用户拒收点翻译成可开发、可验证的改进项：

| 应用 | 用户拒收点 | 改进项 | 验证指标 |
|------|-----------|--------|---------|
| 标题改写 | 用户连续两次指出"超过 30 汉字/60 字节" | 输出后置长度校验、违规自动回炉重写 | 同类约束违反率持续下降 |
| 主图生成 | 首轮没有吸收用户上传的参考图 | 入口提取主体/色调/构图、注入生成约束 | 首轮交付通过率 |
| 采购找品 | "泰规"被当成通用孔，4 轮纠错仍未收敛 | 国别认证变成硬过滤、负反馈压实 Query | 纠错收敛轮数 ≤ 2 |

不捏造"提升了多少"：没有复测结果时，只给明确的验证指标与下一轮实验。

## 自迭代路径：三阶段演进

- **阶段一（过去）人驱动协同**：人选 Case、定范围；人调用 Skill/大模型；人决定改不改——每一步都等人发起
- **阶段二（已落地）评测驱动自迭代**：问题证据 → 自动归因 → 问题路由 → 修复 → 自动回归 → 不退化才准出；重构/换代人工审批、低风险微调自动上线；修正候选 → 线上 Case 验证 → 记录有效修正 → 可回退

变化的是发起权、编排方式和结果消费者。

## 经验清单：8 个坑

1. **只看最终答案**——漏掉工具、数据和交互边界
2. **标准写得很像共识**——没有阈值、证据和门控
3. **评测集过度干净**——线上真实分布完全不同
4. **评测集自身污染**——泄题、矛盾、映射错位
5. **让 Judge 自己算分**——高分偏置与算术错误叠加
6. **一次判太多项**——位置衰减催生模板化偷懒
7. **自动报告只追求快**——错误结论被规模化传播
8. **只给总分不归因**——下游不知道应该修哪一层

大多数失败不在"选哪个 Judge 模型"。如果只能先做三件事：**把完成定义清楚、强制证据、离线与线上同时评。**

## 总结：三个结论

1. **评测的对象不是答案**，而是意图、轨迹、交付和行为边界
2. **Judge 不是终点**，它需要证据、规则闸门与复审 Loop
3. **分数不是价值**，能归因、能回流、能验证修复才是闭环
