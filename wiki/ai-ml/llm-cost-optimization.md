# LLM 成本优化

随着 AI Agent 调用 LLM 的频率和上下文量增长，Token 成本成为关键运营指标。本文综合了成本控制的基础策略，以及毛卓（技术总监，碧桂园服务）在 DataFun「AGENTIC AI 超级智能体系统架构峰会」的演讲《企业大规模AI编程落地，如何控制大模型成本？》的完整实践框架。

## 01 为什么成本很重要

- **ROI 先算清**：投资者三问（AI 带来的收入在哪里？AI 投入的钱算在哪里？AI 最后能不能提高利润率？）。传统企业做项目先算账：业务价值 vs 投入成本。在大规模 AI 编程落地之前必须先回答：这笔投入 ROI 算得过来吗？
- **别被"Token 越来越便宜"麻痹**：Token 单价下降后企业总成本仍可能失控，实际总支出在暴涨。
- **降本和增效不矛盾**（常见误解是矛盾的）：改变敏捷研发模式节省 **2 倍** Token 消耗；研发预算减少一半，工作效率反而翻倍——这是流程重构带来的结构性优化。
- **正循环链条**：节省 Token 降成本 → 输入更高效 → AI 理解更准确 → 输出正确率更高 → 代码质量更好 → 返工率降低 → 研发效率更高。工具替换只能产生局部加速，无法带来系统性效能跃升。
- **未来真实成本公式** = 工资 + Token 消耗 + 提效倍数。示例：优秀者月薪 3 万 + Token 1000 元 + 提效几倍；平庸者月薪 1 万 + Token 2 万 + 提效几倍。1 万工资的员工，实际可能消耗团队 3 万成本（烂代码 Bug 率高、返工不断）。

## 02 Token 消耗在哪了

### 智能体与 LLM 的调用原理

Agent 的核心是 LLM（大脑，负责思考和规划），外加记忆（短期上下文 + 长期知识）与工具（感官和四肢）。规划分为分而治之（Task Decomposition）与自我反思（Self-Reflection）；长期记忆即外部可快速检索的向量索引——RAG。

### 大模型天生没有记忆

Transformer 的 self-attention 每次推理都是纯粹的"输入 → 输出"映射，Q/K/V 全部由当前输入线性变换而来，中间状态全部丢弃。无状态设计是工程选择（同一模型可同时服务数万个并发用户、隐私安全）。用户感觉"AI 记住自己"只是程序把之前对话原样重新塞回上下文窗口，加上人类的心理投射。

**所有让 Agent 有记忆的方案本质上都是在模型外部搭建长期记忆系统**：
- 外部文件存储记忆：ChatGPT 的 Memory 功能、Claude 的 CLAUDE.md 文件
- Agent 记忆系统四层：工作记忆（当前上下文窗口）、情景记忆（具体发生过的事件）、语义记忆（稳定事实）、程序记忆（做事的步骤和技能）

### 分词规则决定 Token 消耗量

Token 是 AI 大模型中读取和生成文本的最小基本单元，Input + Output ≤ 最大上下文长度。不同模型分词器（Tokenizer）不同：中文在英文 LLM 里消耗 Token 较多、在国产 LLM 中通常更省（复合词和成语俚语的分词规则）；英文反之（中文模型会把少见的词切得更碎）。一个汉字大约 1 个 Token（简单词"我""你""好"）、复合词约 2 个汉字 1 个 Token、成语约 4 个汉字 1 个 Token；代码比自然语言更费 Token（缩进空格、换行符单独计数），结构化数据走 JSON 比 YAML 更贵。

### 大模型输出比输入更贵（3-5 倍）

| 维度 | Prefill 阶段（"读题"） | Decode 阶段（"答题"） |
|------|----------------------|----------------------|
| 核心任务 | 一次性并行处理所有输入 Token | 基于已有内容逐字（串行）生成新 Token |
| 计算类型 | 计算密集型（Compute-Bound），GPU 算力是瓶颈 | 内存密集型（Memory-Bound），显存带宽是瓶颈（KV Cache） |
| 性能指标 | TTFT（从提问到出现第一个字的时间） | TPS（每秒生成 Token 速度） |
| 资源消耗 | 算力消耗高但持续时间短 | 单次算力低但持续时间长，随输出长度线性增长 |
| 优化可能 | 提示词缓存（Prompt Caching）复用计算结果 | 优化空间有限，必须逐字进行、难以并行 |

示例价格：Sonnet 4.6 输入 **$3/百万 token**、输出 **$15/百万 token**。

### 日常开发 Token 花在哪里了（Claude Code 真实消耗分析）

| 日常编码消耗来源 | Token | 占比 | 说明 |
|------------------|-------|------|------|
| 系统提示与会话初始化 | ~1 万 | 10% | 每次会话固定开销 |
| 工具调用累积上下文 | ~4 万 | 40% | Read/Grep 返回内容不断累加 |
| AI 思考与生成代码 | ~2 万 | 20% | 真正"干活"的部分 |
| 返工修复（幻觉/调试） | ~2 万 | 20% | AI 写了错误代码，反复修改 |
| 其他（格式化/解释文字） | ~1 万 | 10% | 解释性文字、不必要的格式化 |

固定开销构成：系统提示词、工具名称、MCP 工具、Skill、自定义 agent、记忆文件等。演讲引用的 GitHub issue（anthropics/claude-code #52979）示例：Claude Code CLI 中简单 prompt 也消耗约 2-3 万 Token——"hi" 约 31,000 tokens、"what colour is the sky?" 约 19,000 tokens（截图数据）。

## 03 技术——优化上下文

### 大模型维度：分层路由不同级别模型

让任务复杂度与模型能力精准匹配（杀鸡用鸡刀，杀牛用牛刀）：

| 级别 | 模型 | 适用任务 | 任务难度 |
|------|------|---------|---------|
| 经济型 | Qwen3.6-flash、Haiku | 代码补全、格式化、简单重命名、简单测试 | 不需要复杂推理，有明确的执行规则 |
| 均衡型 | Qwen3.7-Plus、Sonnet | CRUD 开发、功能开发、接口实现、测试编写 | 需要理解上下文，但范围可控，有一定执行标准 |
| 推理型 | Qwen3.7-max、GLM-5.2、Opus4.8/fable | 架构设计、复杂重构、疑难排查 | 需要深度思考和创造性思维，综合深度推理 |

Extended Thinking 按需开启：思考过程 Token 按输出价格计费，动辄数万输出；只有复杂推理任务才需要开启扩展思考。

落地示例：在 `~/.claude/settings.json` 配置模型别名（`ANTHROPIC_DEFAULT_HAIKU_MODEL`/`SONNET`/`OPUS` 映射到 qwen3.6-flash/qwen3.7-plus/qwen3.7-max）；创建 fast-worker（haiku）与 deep-thinker（opus, effort: high）子代理；在 CLAUDE.md 写路由规则（简单任务 → fast-worker，复杂任务 → deep-thinker，日常开发自己处理）。

### 架构维度：模块解耦和无状态

- 缩小 AI 可触碰代码范围；同一个需求，不同架构差 **3-5 倍** Token；"在 Prompt 层抠 30%，不如在架构层省 300%"。
- AI 时代新度量：Modification Surface / Context Boundary。

| 架构形态 | 单任务 Token 消耗 | 返工率 |
|---------|-----------------|--------|
| 大泥球单体 | 40-100 万 | 40% 以上 |
| 分布式大泥球（伪微服务） | 50-120 万 | 45% 以上 |
| 契约化模块架构 | 5-15 万 | 低于 15% |
| 真微服务（强契约） | 5-15 万 | 低于 15% |

落地动作：Fitness Function（ArchUnit）把架构约束代码化；契约先行（OpenAPI / Protobuf）——人定契约、AI 填实现；模块化单体优先于伪微服务。

### 输入维度：高效高质量的会话

- 一个任务一个会话，每任务控制在 **5-8 轮**对话内；超过 10 轮强制保存状态开新会话；用 `/resume` 续接避免重复加载上下文。
- 按架构拆分会话、按任务原子性拆分会话；同类小任务合并（共享上下文）。
- 子代理独立干重活：子代理的本质是"一次性探索员"，独立空间执行搜索等重任务，只回传关键结论并自动销毁，主会话保持上下文纯净。
- `/compact` 有损压缩，节省 **>80%**（可指定保留项）；`/clear` 彻底清空（完全切换任务时）；铁律：一个会话只解决一个独立任务。
- **缓存命中**：不变内容只付一次费；Claude 缓存命中打 **1 折**、GPT-4 打 5 折、Gemini 打 2.5 折。把不变内容（CLAUDE.md）放最前面、变化的任务描述放最后面；任务间传递"变更摘要"（.ai-memory/task-a-summary.md）而非完整上下文。
- **精准提示词**：公式化提问与限制行为范围（在什么文件里做什么、用什么方法、具体怎么干）；上下文管理三原则：只给必要信息、排除无关文件（.claudeignore）、过滤无效信息（日志过滤、diff 切片、输出摘要）。错误示例（"你是一个资深 Java 开发者，精通 Spring Boot…"）vs 正确示例（"基于 Controller 模板，创建充电桩管理接口：POST /api/v1/charging-stations。字段：stationNo(String)…"）。
- **Skill 动态加载**：CLAUDE.md 每轮对话全量加载，内容过多造成巨大浪费——瘦身只保留最常用核心规则（技术栈、关键目录、禁用技术）；低频规范做成按需加载的 Skill，只有触发时才消耗 Token。原则：高频规则用 CLAUDE.md，低频指令用 Skill。
- **MCP 按需加载**：MCP 工具定义每次对话全量加载到系统提示词，即便不使用也占用大量 Token；按需开关（只开当前任务真正需要的 MCP，用完即关）；启用 MCP-CLI 模式可将 MCP 相关 Token 消耗降低约 **85%**；用 `/context` 查看 MCP 占用。

### 输出维度：精简输出与结构化输出

- 三句金指令：① 只输出代码 ② 不要重复已有代码 ③ 用 diff 格式输出。在 CLAUDE.md 写输出规范（不要"好的""当然可以"等确认语和"总结一下"等结尾语）；用 JSON Schema 约束输出格式。
- **模板复用**：建立代码模板库（.ai-memory/templates/：Controller/Service/Mapper/CreateReq/VO/PageReq/IntegrationTest 模板），基于模板只替换占位符（{Entity}、{entity}、{api}）。

### 软件工程维度：Harness 工程

核心思想：与其让 AI 每次都从零写代码，不如提前搭好"脚手架"，让 AI 只需要填充差异部分。六层 Harness：

| 层 | 名称 | 具体内容 | 效果 |
|----|------|---------|------|
| 1 | 项目脚手架 | 项目结构、模块划分、技术栈定义 | 清晰的 Harness 工程目录 |
| 2 | 代码模板库 | Controller/Service/Mapper 等标准模板 | AI 从"写代码"变"填代码"，省 60-80% |
| 3 | API 契约 | 接口定义、请求/响应 Schema（OpenAPI） | AI 直接读取不用猜测，减少"猜错→修改→再猜错"循环 |
| 4 | 测试 | 单元测试框架、Mock、测试数据（JUnit5 + Mockito + SpringBoot Test、BaseIntegrationTest 基类、TestDataLoader） | 测试框架自动告诉 AI 哪里写错了，减少调试循环约 50-70% |
| 5 | 构建 | Dockerfile、Maven 配置、环境配置（统一父 POM、多阶段构建、Checkstyle、SpotBugs） | 结构已定义，减少幻觉和返工 |
| 6 | CI/CD | 自动化流水线、代码检查、部署脚本 | 有问题精准反馈给 AI，格式类问题提交前自动修复，不浪费 Token |

## 04 管理——创新研发流程

### AI 编程时代的新研发模式

打破团队边界、职位边界、传统管理模式；人尽其用、强者带教。新研发模式（示例团队 20 人）：
- **20 人团队全员分 4 组写 PRD 需求**（产品经理带队）——需求标准：直接编写可输入给 AI、且 AI 可识别的 PRD 标准需求，消灭需求层层传递讲解
- **架构师 2 人**写技术规约、写架构设计文档
- **4 名核心工程师**：AI 编程，精通规约编程、与 AI 高效沟通（发挥老工程师需求理解优势，能力弱的工程师聚焦需求梳理并带教学习）
- **团队全员**：测试 + 验收——谁写的需求谁验收，需求无需传递

旧模式问题：管理沟通耗时、需求传递链路太长（产品→开发→AI→测试）、重复需求撰写、工程师单兵作战（每人按自己模块 AI 编码、缺少全局思考、标准不统一）、大规模多人协作易冲突。

### 多人写 PRD + 少数人写代码

核心逻辑：把成本花在执行 AI 一次做对上，而不是让 AI 反复做错再改。结果：**研发效率翻了一倍，Token 消耗减少一半**。

| 环节 | AI+流程重构后 | 提效逻辑 |
|------|--------------|---------|
| 需求沟通与对齐 | 多人协同写 PRD，前置消化歧义 | 节省约 50% 沟通成本 |
| AI 代码生成 | PRD 精准，AI 一次生成准确率高 | 返工率从 40% 降至 15% 以下 |
| 调试与返工 | 需求清晰，边界条件已在 PRD 中覆盖 | 节省约 60% 调试时间 |
| Code Review | 代码结构清晰，Review 聚焦核心逻辑 | Review 周期缩短约 40% |

### 研发流程瓶颈：人工代码评审慢

AI 让写代码快了 2-3 倍，但 Review 只快了 30%；每人每天代码量从 200 行 → 600 行；Reviewer 负担从检查作者逻辑变成验证 AI 意图；微 PR 累积风险让整体架构悄悄腐化。AI 代码 5 个新增检查维度：幻觉 API、License/IP 污染、安全漏洞、架构约束符合度、可维护性。四层防御（Defense in Depth）：L1 自动化检查（静态分析、安全扫描）→ L2 AI 辅助 Review（验证意图、架构符合度）→ L3 人工 Review（业务逻辑、关键判断）→ L4 测试验证（覆盖率、断言质量）。

### 防返工：质量、测试、可维护性

- 效能度量：效率（代码接受率、PR 周期）、质量（引入 Bug 率、覆盖率）、成本（单需求开发成本）、团队（采纳率、满意度）。
- 测试结果的虚假安全：覆盖率高但关键路径断言低；AI 生成测试和代码同源错误（AI 写代码用了错误假设，AI 写测试用了同样的错误假设 → 测试和代码一起错）。
- 生成代码的维护难度：代码读者从人变成人与 AI；沿用旧规范 = 制造隐形技术债；注释从简洁走向结构化、命名从简短走向明确无歧义。
- 代码库的新角色：**AI 的操作系统**——代码规范面向 AI 重构；文档体系升级（ADR、CLAUDE.md、Decision Log）；模块边界从软约定变为强契约（OpenAPI）。

## 05 人才——注重综合能力

- **Vibe Coding vs 规约编程**：Vibe Coding 仅凭感觉或模糊想法让 AI 生成代码、完全不理解背后逻辑和风险——创业小公司系统挂了就挂了，但大型企业发生故障时掌控者必须有能力修复。Harness 和规约编程以人为本，人始终是软件产品的主人；技术够强才能 SDD 和 Harness，才能掌控 AI。
- **能力差距在 AI 时代被 Token 放大**：同样的任务，不同的人 Token 消耗可以差出整整一倍（甚至一个数量级）；优秀工程师用少量 Token 换来数十倍产出；招工资高但能力强的工程师，企业支出综合成本更低。
- 优秀工程师画像：架构能力（AI 产出系统稳定，减少重构成本）、逻辑清晰（一次指令到位）、沟通精湛（减少返工）、工程理解深（全流程提效）、业务思维强。
- **用流程制度倒逼 Token 消耗优化**：通过机制、制度保障项目预算不超标，员工主动降低 Token；不只看"省了多少 Token"，更要看"每个 Token 产出了多少业务价值"。
